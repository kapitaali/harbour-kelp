## 2. Bugs found and fixed in this session

These are the most valuable part of this document: none of them was caught by the
unit tests, and two of them were invisible to the emulator because of how it was
being launched.

### 2.1 A fresh install could not write anything (Sailjail data directory)

**Symptom.** On the phone, after a normal install: the app ran, showed a share,
but `~/.local/share/harbour-kelp/kelp.log` did not exist and neither did the
object store. `find / -name kelp.log` found nothing. Only
`~/.local/share/harbour.kelp/` was created, and it stayed empty.

**Cause.** The app asked for `~/.local/share/harbour-kelp`. Under Sailjail that
directory is not provisioned and the sandbox will not let the app create it.
Sailjail provisions exactly one data directory, built from the desktop file's
names — `OrganizationName=harbour.kelp`, `ApplicationName=harbour-kelp` — giving
`~/.local/share/harbour.kelp/harbour-kelp`, and hides the rest of
`~/.local/share`. The `--mkdir`/`--whitelist` pairs in the `firejail` command
line show this plainly:

```
--mkdir=${HOME}/.local/share/harbour.kelp/harbour-kelp
--whitelist=${HOME}/.local/share/harbour.kelp/harbour-kelp
```

So `KelpLog::install()` — the first thing `main()` does — could not create its
directory, and neither could the object store. Sealing had nowhere to write.

**Why it stayed hidden.** Development ran on the emulator with the app launched
from a shell, i.e. *unsandboxed*, and `~/.local/share/harbour-kelp` already
existed there from earlier runs. Deleting that directory and launching under
`sailjail` on the emulator reproduced the phone's symptom exactly.

**Fix.** `src/harbour-kelp.cpp` sets `OrganizationName`/`ApplicationName` before
any path is asked for, and `KelpLog::dataDirectory()` (`src/kelplog.{h,cpp}`)
returns `QStandardPaths::writableLocation(AppDataLocation)` — the directory
Sailjail provides, and the same path sandboxed or not. It moves an existing
`~/.local/share/harbour-kelp` into the new location once, so bundles sealed by an
earlier build keep working. Both the log and the object store use that one
function; nothing else should invent a path.

**Guard.** None in code. The check is a clean-install launch under Sailjail:

```sh
ssh -p 2223 -i $KEY defaultuser@127.0.0.1 '
  rm -rf ~/.local/share/harbour-kelp ~/.local/share/harbour.kelp
  cd / && setsid env XDG_RUNTIME_DIR=/run/user/100000 \
    DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/100000/dbus/user_bus_socket \
    WAYLAND_DISPLAY=../../display/wayland-0 QT_QPA_PLATFORM=wayland \
    sailjail -p harbour-kelp /usr/bin/harbour-kelp >/dev/null 2>&1 </dev/null & sleep 7
  ls -la ~/.local/share/harbour.kelp/harbour-kelp/'
```

### 2.2 The link could not be recovered from the log

**Symptom.** The link was searched for in `kelp.log` and was not there.

**Cause.** Deliberate: `KelpBundles` only writes the link when the app is
launched with `KELP_DEBUG_LINK=1`, because a link is a capability and its
fragment is the decryption key — logging it by default writes the key into a
plaintext file. Reasonable in general, wrong for this workflow: the emulator has
no usable clipboard, so reading the link out of the log is the *only* way to
hand it to another device.

**Fix.** Done, as proposed. *Settings → Include links in the log* is a persisted
switch, off by default: `src/kelpsettings.{h,cpp}` stores it in an INI file in
the app data directory (not `~/.config`, which the sandbox hides), and
`KelpBundles::seal` consults it before writing the link. `KELP_DEBUG_LINK=1`
still forces it on for a single run, so existing headless scripts keep working.
The switch's own description spells out that a link holds the key. Verified on
the emulator (§3.5) and covered by a restart unit test (§3.2).

### 2.3 LAN fetch always answered 401 ("the sender did not recognise this link")

**Symptom.** Pasting a valid link and tapping *Download* failed immediately with
*the sender did not recognise this link — it may have stopped sharing* (the app's
text for a 401). Meanwhile, from the same machine, `curl` with the correctly
encoded token against the same URL returned `200` and the right JSON.

**Cause.** When the fetch loop was factored behind `KelpSource`
(`src/kelpfetch.{h,cpp}`), `LanSource` was handed the **raw 32-byte** swarm token
and put it straight into the header:

```cpp
request.setRawHeader("Authorization", "Bearer " + m_token);   // raw bytes
```

The sender base64url-decodes that header value and compares bytes, so binary
garbage decodes to nothing and mismatches — a 401, indistinguishable from a wrong
token by design (no enumeration oracle). `RelaySource` was unaffected because it
puts the token in a URL path and encodes it there. `KelpClient` had done it
correctly before the split.

**Why it stayed hidden.** Every relay test stripped `l=` from the link, so the
LAN path was never exercised after the refactor, and the C2b device test predated
it. The `curl` checks passed because they used a hand-encoded token — that
mismatch between "curl works, app doesn't" is what located it.

**Fix.** `KelpSource::create` encodes the derived token before constructing the
source, and the member is now named for what it holds:

```cpp
return new LanSource(base, Kelp::Link::base64UrlEncode(swarm).toLatin1(),
                     link.lan, bundleIdText, parent);            // kelpfetch.cpp:415
```

**Guard.** `src/tests/tst_kelpfetch.cpp` (+ `tst_kelpfetch.pro`,
`run-kelpfetch-test.sh`; run it with `sfdk -c
target=SailfishOS-5.1.0.11-i486 build-shell sh
src/tests/run-kelpfetch-test.sh`). It builds a link with `l=`, goes through
`KelpSource::create` the way the client does, and asserts on the requests
`LanSource` actually sends: `Authorization` equals `Bearer ` +
`base64url(swarmToken(secret))` (43 chars for 32 bytes — raw bytes would be 32),
the paths are `/v1/bundle/<b32>/info` and `/v1/bundle/<b32>/object/<b32>`, and
the header value decodes (the sender's step) back to the token bytes. A link
naming neither address nor relay returns nullptr. Negative control verified:
with the encoding removed the test fails 4 checks; with it, 17 checks,
0 failures.

### 2.4 *Stop sharing* from the list did not stop serving

**Symptom.** Stopping a share from the **Bundles** list removed the row but left
the bundle being served: it stayed fetchable by anyone holding the link, with
nothing left in the list to stop it.

**Cause.** The long-press menu item in `BundlesPage.qml` only did
`bundlesModel.remove(index)`. The **Bundle** page's own *Stop sharing* button did
it correctly (`unshare`, then remove); the list's context-menu path predated that
and was never brought in line. A disappearing row looks exactly like a stopped
share, so nothing surfaced it.

**Fix.** The list handler now mirrors the page — `kelpBundles.unshare(bundleId)`
before the row goes, then `store.saveShares()` so the stopped share is not
restored at the next launch either. The bundle id is read *before* the removal
(`bundlesModel.get(doomed).bundleId`), because the snapshot is gone afterwards.

### 2.5 An unreachable sender was reported as a sender that "stopped answering"

**Symptom** (found by the user, not by a test). Sharing from the emulator and
fetching from another device failed with *"the sender stopped answering"*. The
emulator's own log showed it serving fine on `10.0.2.15:<port>`.

**Cause.** The emulator sits behind QEMU's *user-mode* NAT: it can dial out, but
nothing outside can dial in to `10.0.2.15`. Measured directly — the emulator
reaches the host (`200`), the host cannot reach the emulator (`curl` exit 28,
timeout). A dropped SYN is not an error the socket ever sees, so no HTTP status
came back and `KelpClient` sat until its 20 s silence deadline (`kSilenceMs`),
whose message blames a sender that had never actually been heard from. The
message was technically true and diagnostically wrong.

**Fix.** Not a reworded message on the silence deadline — a reachability probe
*before* it. `LanSource`'s first request (`begin()`) must now produce some sign
of life — response headers, or a finish carrying an error — within `kConnectMs`
(8 s); `RelaySource` must reach TLS within `kRelayConnectMs` (10 s). Any answer,
even a refusal, stops the probe, so the silence deadline keeps its real meaning
(the sender answered, then went quiet). The timeouts are deliberately generous
rather than snappy: failing a slow-but-present peer would be a worse bug than
waiting a few extra seconds.

### 3.7 Shares survive a restart (Next Move 3, verified live)

The shared rows were memory-only: a restart dropped every share even though the
sealed objects stayed on disk. And the only address a link carried was the one
captured at share time. Now the rows are written to `shares.json` beside the log
(mode `0600` — it holds the key) and restored at startup, where each is served
again and given a **fresh** link, because the LAN port is ephemeral. `seal()` and
the new `republish()` share one `publish()` helper, so a restored bundle is
published exactly like a fresh one.

Verified on the emulator with two app instances in one guest (`XDG_DATA_HOME`
split), a 200 KiB random file, and a temporary Timer hook in the installed root
QML (backed up first, restored after — the installed file's md5 matches the
build's again). No `#k=` fragment is written here: a link is the key.

Run 1 — fresh data home, seal and save:

### 3.8 The link as a QR code (user-requested, verified by scanning)

The Bundle page had a QR *placeholder*. It now renders a real code: the whole
`kelp://` link, key included, so a recipient can scan it instead of retyping it —
the shortest path from the device that sealed a bundle to the device that opens
it, and the only one that does not need a clipboard.

The encoding is Project Nayuki's QR Code generator library, vendored unmodified
as `src/qrcodegen.{hpp,cpp}` (MIT; the notice ships in `src/qrcodegen.LICENSE`
and is installed with the app). `src/kelpqr.{h,cpp}` is the Qt Quick item:
byte mode at ECC M, automatic version, whole-pixel modules black on white with
the standard four-module quiet zone, and `valid=false` when there is no link, so
the page can say so instead of showing a blank square. It is registered as
`KelpQrCode` in the `harbour.kelp` URI the page imports. The item is a pure view:
it holds the link only to draw it and never logs or stores it.

Two independent verifications:

1. **The encoder, against a different implementation.** A 25×25 matrix (byte
   mode, version 2, ECC M, mask 3, payload `kelp://abc/12345678`) was produced by
   Python's `qrcode` with those parameters fixed and pinned in
   `src/tests/tst_kelpqr.cpp`; the vendored encoder reproduces it bit for bit.
   The same test walks the app's real path (a real-shaped link, byte mode, ECC M,
   automatic version) and checks it is a well-formed QR, plus the too-long
   refusal. 9 checks, 0 failures.

2. **The rendered code, actually scanned.** On the emulator a temporary hook
   pushed the Bundle page, opened its QR dialog, and grabbed the `KelpQrCode`
   item to a PNG; a real decoder (zxing-cpp) read the PNG back. The decoded text
   has the same length and the same rolling hash as the link the page was
   showing:

   ```
   TESTSET: restored count=1 lan=10.0.2.15:37069 state=seeding linkLen=139 linkHash=450514377
   TESTSET: qr=found valid=true size=318x318
   DECODED format=QR Code len=139
   decoded: len=139 hash=450514377
   ```

   No `#k=` fragment is written down: the link never left the device, and only
   its length and a non-reversible hash crossed to the host to be compared.

Emulator left clean: hook restored (0 markers, the installed QML back to the
build's), the split data directory, the source file, the captured PNG and the
temporary scripts removed, no `harbour-kelp` process running.

Carried forward: `KelpBundles::republish()` does **not** log the link even when
*Include links in the log* is on — only `seal()` does — so a restored share's new
link shows in the UI and in the QR but not in the log. See §9.

### 3.9 "Could not reach the sender" vs "the sender stopped answering" (verified live)

The user's symptom (§2.5) reproduced on purpose: a host listener that accepts TCP
and then stays silent — the exact shape of an address behind a NAT with no way
in — with the app pointed at it by a throwaway link.

Silent peer (nothing ever answers):

```
13:25:26.715 KelpClient: fetching "aaaqeayeaudaocaj" from "10.42.0.228:8098" as "probe"
13:25:34.957 KelpClient: fetch failed: "could not reach the sender — no answer from 10.42.0.228:8098"
```

That is **8.2 s** and the right cause; before, it was 20 s and *"the sender
stopped answering"* — which a sender that was never contacted cannot be said to
have done.

Control — a peer that *does* answer, with a refusal (a host server returning

13:26:36.474 KelpClient: fetch failed: "the sender did not recognise this link — it may have stopped sharing"

### 3.10 Withholding the local address from links (user-requested, verified live)

> **Partly superseded by §3.11.** The `l=` below is the plaintext form that §3.11
> replaced with a sealed `q=`; the switch described here is unchanged, and still the
> answer for a share that must not name the publisher at all.

A link is handed to whoever it is sent to — and to whoever they forward it to — and
`l=` names the publisher's **own** interface address, so it is disclosed to all of
them. The user asked whether a link shared across the globe leaks their IP. It
does: on Wi-Fi the address is private (`192.168.x.x`, meaningful only on that LAN,
which is what design §3.1 assumes), but `KelpServer::lanHostAddress()` falls back
to a point-to-point bearer and `usable()` accepts any non-loopback IPv4, so with
Wi-Fi off `l=` can be the phone's carrier-assigned address.

The new global switch **Settings → *Include my local address in the link*** (on by
default; `KelpSettings::includeLanAddress`) withholds it: `publish()` skips the LAN
block entirely, so nothing is served locally and the link carries no address — a
relay then carries it. Off has a cost worth stating in the UI: a share with no
relay has nowhere to be fetched from.

### 3.11 Sealing the address in the link (user-requested, verified live)

The switch in §3.10 answers "should the link name me at all". The follow-up ask was
narrower: *keep sending the address, but do not send it in the clear.* Hashing cannot do
that — a hash is one-way, so a recipient could never recover a `host:port` to dial — so
the address is **encrypted** instead, under a key derived from the link's own fragment.

`Link::encode` now writes the publisher's address and the share's label into one `q=`
field:

```
q = base64url( nonce(12) ‖ AES-256-GCM(key = HKDF(secret, "kelp/v1/link"),
                                       aad = bundle_id,
                                       plaintext = CBOR{ "l": host:port, "n": label }) )
```

No new primitive: `Kelp::Crypto` already had AES-256-GCM and HKDF, and `kelp/v1/link` is
simply a fourth independent HKDF output beside content/swarm/relay. The recipient holds the
fragment, derives the same key and dials.

What that buys is worth stating plainly. The key rides in the same link, so **whoever the
link is sent to can open the block** — the address is not hidden from the recipient, who
needs it to connect. It *is* hidden from everything that sees the link without its
fragment: a redacted paste, a chat or link preview, a log, and — the case that will matter
— a browser gateway, which by convention is handed the query but not the fragment. Binding
the block to the bundle id as associated data means it cannot be lifted from one link into
another.

Compatibility is deliberately one-way. `decode` still accepts a plaintext `l=`/`n=` link,
so links and QR codes already out there keep working, and a link carrying both prefers the
sealed block. But an older *reader* finds no address in a new link and falls back to a
relay — so the phone must be updated to the new build for the LAN fast path. The link grows
from 141 to ~190 characters (`q=` is ~83), which moves the QR up about one version; it
still scans.

Verified:
* `libkelp` — 312 checks (was 304). New: a sealed round-trip; the address's host part and
  the label are absent from the link text; a legacy plaintext link still decodes; a flipped
  byte in `q=` is refused; and a block sewn onto another bundle id is refused (the AAD).
* `src/tests/tst_kelpfetch.cpp` — 37 checks (was 29): `encode → decode → KelpSource::create`
  lands on the same `host:port`, which is the recipient's whole path.
* `tst_kelpbundles` — 22 checks, unchanged in count; its helper now decodes the link to ask
  whether it names an address, so the §3.10 gate still holds.
* Live, on the emulator: the app logged `KelpServer: bound to "10.0.2.15:45525"` and
  `serving on "172.28.172.3:45525"`, then a link with neither the address nor the name in
  its text (`…?q=XxaBVSC…`). Through the host forward, an authenticated `/info` — token

### 3.12 Storage management: seeing and reclaiming what nothing needs (design §12.7, verified live)

The last open design question with teeth. Every seal and every fetch writes objects into one
deduplicated store and **nothing ever deleted from it**; the count and size were visible on the
About page, but there was no way to reclaim a byte. On this device the store had already drifted
from 22 to 33 objects — the difference being what earlier fetch tests left behind.

The obstacle is that "unused" cannot be answered per bundle. The store is one pool with dedupe,
so an object may belong to several shares at once, and there is no reverse index from an object
to the manifests that name it (the graph points down, not up). The only sound definition is
global: *the objects every share on this device reaches, walked in full*. Everything else is
either what a fetch left behind or what a share that is gone no longer needs. Downloads
themselves are ordinary files in `Downloads`, so their cached objects are disposable — removing
them costs a re-download, not the content.

That walk is `Kelp::bundleObjects(store, key, rootId, &ids, &error)`, new in `libkelp`. It is the
same traversal as the fetch planner, with two deliberate differences. It **notes an id as it
visits it** rather than only when it is absent, so a whole bundle enumerates instead of returning
an empty "missing" list. And it is **strict about manifests**: every manifest must be present and
must open with the key. That is the safety property the whole feature rests on — the entries under
an unreadable manifest are unknown, so a list that cannot account for them must not be used to
decide what is unreferenced. Data objects are only *named* by their manifests, never read, so a
bundle whose chunks have holes still enumerates completely.

The app side needed only two calls. `KelpBundles::storeUsage(shares)` returns total objects/bytes,
the subset the shares need, and the difference; `pruneStore(shares)` deletes exactly that
difference. Both take the share rows **from the UI** (`store.bundlesModel`) rather than reading
`shares.json` back, so "in use" is exactly what the device is really serving. If any row cannot be
walked, both refuse and delete nothing — a share that cannot be read must never have its objects
mistaken for junk. The store gained `objectIds()` (walks the sharded tree; a half-written `.tmp`
never passes the id-length check), `objectSize(id)` and `remove(id)`.

Settings → **Storage** shows the breakdown and offers **Remove unused objects** behind a confirm
dialog, enabled only when there is something to remove. The wording is honest about what it
costs: the leftovers are a cache, and anything fetched from a link again is downloaded once more.

Verified:
* `libkelp` — 345 checks (was 312). New: a sealed bundle lists exactly the store's contents
  (every manifest and every chunk, nothing invented); no id twice; the wrong key fails rather
  than returning an empty list; dropping a *data* object leaves the listing complete while
  dropping a *manifest* is refused; a missing root or a stub id fails.
* `tst_kelpbundles` — 54 checks (was 22). New: a sealed share reports every object in use and
  zero unused; a stray object is reported as the only unused one; clean-up removes it and every
  object the share needs survives, root included; a second clean-up removes zero and succeeds;
  and a share whose stored key no longer opens its manifests makes *both* calls refuse, leaving
  the store — stray and all — untouched.
* Live, on the emulator, through the real Settings page (created from the installed QML):
  `usage-before`: 33 objects, 3.6 MB, in use 22 (1.6 MB), unused 11 (2.0 MB). `prune removed=11
  freed=2136892`. `usage-after`: 22 objects, in use 22, unused 0. The share's 22 objects were
  byte-for-byte the same set afterwards, and the app kept serving it. The store was tarred before
  the run and restored afterwards, so the device was left exactly as it was found.

One QML trap worth recording: Sailfish's `Dialog` has **no `title` property** — the title is the
`DialogHeader` inside it. The page failed to load with `Cannot assign to non-existent property
"title"`, which is invisible until the page is actually opened (or compiled by a test hook), so
every other run would have missed it.

### 3.14 The publisher's own view of a fetch (verified live)

The debugging session in §3.13/§2.5 exposed the gap this closes. The server logged **nothing per
request**: a recipient that fetched all 125 objects and one that never arrived left exactly the
same trace in the publisher's log — none. The app has a logging feature precisely so a problem
can be diagnosed from the device, and the half that was being diagnosed was invisible in it. The
only way to know a fetch had happened was to ask the person holding the phone.

`KelpServer` now tallies what each peer asks for (`Traffic`, `src/kelpserver.{h,cpp}`):

| counter | what it is |
|---|---|
| `requests` | authenticated `/info` calls — the client makes one at the start of every fetch, so this is *fetches started* |
| `objects` / `bytes` | objects actually written out, and their size as stored (ciphertext) |
| `refused` | `401`s: a link the server does not know or a token that did not match |
| `bundle` | the name of the last share involved, so the line reads as something |

The tally is keyed by **peer address, not address:port** — every request arrives on its own
connection (`Connection: close`), so a port would make each object look like a new peer. It is
written as **one line per peer**, about five seconds after that peer's last request, from the
sweeper that already tidies half-open connections; nothing logs per object. That keeps the
useful signal (did anyone fetch, and did they get all of it) while a busy share cannot turn into
a log flood, and a run of failed attempts costs one line with a count rather than one line each.

```
KelpServer: "10.0.2.15: 1 fetch(es) started, 1 object(s), 102 byte(s) of \"Screenshots\"; 3 request(s) refused"
```

Unlike links, this is **not** behind a setting: a traffic line carries no key, only counts, byte
sizes, a share name and an address, in the publisher's own local log. The share name had to be
added to `KelpServer::share()` for it — the server was never told one — which is why the line can
say *"Screenshots"* instead of *"a bundle"*.

Verified:

* `tst_kelpbundles` — **79 checks** (was 54). The new test drives the **real listener over a real
  socket** (a hand-written HTTP GET): an authenticated `/info` answers 200 and the tally shows
  one fetch started, no objects, and the share's name; an authenticated GET of the root object
  answers 200 and the tally shows exactly one object and exactly the bytes the body carried; an
  `/info` with no token and one with the wrong token are both `401` and counted as refusals, with
  `requests` and `objects` untouched; an unknown bundle is refused and counted too.
* Live, on the emulator, over the host bridge and **inside the sandbox** (the app was launched
  with `sailjail -p harbour-kelp`, so this ran under firejail with the real permission profiles):

  ```sh
  src/tests/run-emu-share.sh --host 172.28.172.3 --redact --fetch
  ```

  ```
    /info           right token -> 200 {"v":1,"objects":125,"files":26,"bytes":23257981}
    /object/<root>  right token -> 200, 102 byte(s)
    /info           no token    -> 401 (want 401)
    /info           wrong token -> 401 (want 401)
  result: serves

  KelpServer: "10.0.2.15: 1 fetch(es) started, 1 object(s), 102 byte(s) of \"Screenshots\"; 3 request(s) refused"
  ```

  Every number matches what was asked for: one fetch, one object, its 102 bytes, and three
  refusals — two from the probe, plus the script's own unauthenticated reachability check.

`src/tests/kelp-probe.py` (new) is the probe: it reads the publisher's log on stdin, picks up the
newest link, derives the bearer token the way `libkelp` does (HKDF-SHA256, 32 zero-byte salt,
info `kelp/v1/swarm`), and makes those four requests. The `#k=` fragment **is** the key, so it is
parsed and never printed — the output is status codes and sizes only, safe to read or paste. It
checks reachability, authorisation and that objects leave the device: everything except the
recipient's own crypto. `run-emu-share.sh --fetch` runs it against the forward and then prints
the publisher's line for that traffic, so a share can be checked *before* it goes to a phone.

**This covers the LAN path only** — the relay half is §3.15.

Two traps this cost, both recorded in §6: the listener lives in the same thread as the test, so a
test that blocks in `waitForConnected`/`waitForReadyRead` is never accepted — the event loop has
to run; and Sailfish's Qt is **5.6**, where `QAbstractSocket` has no `errorOccurred` signal
(that is 5.15) and `QOverload` does not exist (5.7), so the socket-error overload is selected with
an explicit cast.

### 3.15 …and the same for the relay path (verified in the relay harness)

The gap §3.14 left open was the *cross-network* half — the one with the most ways to fail, since a
fetch there needs the publisher's dial-out to have survived, TLS to have come up, the relay to
have forwarded the WANT, and the object to have been found in the store. `KelpTunnel` now keeps
the same account, per tunnel rather than per peer (the relay multiplexes recipients, so a per-peer
count is not knowable from this side):

| counter | what it is |
|---|---|
| `wanted` | WANT frames: objects a recipient asked for through this tunnel |
| `objects` / `bytes` | DATA frames sent, and their size as stored |
| `rejected` | REJECTs: wanted, but not held here — a stale share, or a bug worth chasing |

It is reported the same way, from a single-shot timer that every WANT restarts, so it costs
nothing while idle and lands about five seconds after a transfer stops. It is also reported on
teardown — a tunnel that drops, or rotates to the next relay, writes what it served first, so a
transfer interrupted by a reconnect is still accounted for and the line names the relay it was
actually on.

```
KelpTunnel: "127.0.0.1:9643: 2 object(s) wanted, 1 served (27 byte(s)), 1 not held of \"relay test\""
```

**The relay harness now runs this code instead of a stand-in.** `relay/test/relaytest.cpp` used
to hand-write the publisher's half of the wire protocol — which meant the relay was tested
against a re-implementation, and a bug in the app's own framing or state machine could not be
caught by it. It now builds the app's real `KelpTunnel` on a real `KelpObjectStore` and lets it
register and serve, so the same code the device runs is what the relay answers.

Verified: `relay/test/run-relay-test.sh` — **6/6 ALL PASS** (was 4), with two new cases:

```
PASS tunnel tallied the transfer — wanted=2 served=1 bytes=27 notHeld=1
PASS tunnel reported itself and reset — wanted=0 served=0
```

The first pins the count against what the harness actually asked for: two objects wanted (the one
held here, and one it does not have), one served, its 27 bytes, one not held. The second is the
proof that the log line really ran — reporting resets the tally, so an empty tally afterwards is
the evidence. The line above is the app's own `qInfo`, printed by the harness
(`QT_LOGGING_TO_CONSOLE=1`, which the run script now sets for both halves).

Scope, stated plainly: this was verified **in the harness**, which is a real relay over real TLS
1.3 with the app's own tunnel as the publisher — not re-run live on the emulator today. The relay
path itself was verified live during C3, and what is new here (the tally and its report) is shared
with the LAN path, whose live check is §3.14. Nothing on the device is configured with a relay
(`Kelp: relays =`), so a live pass would need one running and reachable first.

### 4.5 Reach the emulator's share from the LAN

The emulator cannot be dialled into (§6), so a link it mints names `10.0.2.15` and is
useless to any other device. Since §3.11 the app seals the address it advertises, so
only the app can name the host in a link: launch it with that address and link logging
on, then bridge the port.

In the guest:

```sh
cd / && setsid env XDG_RUNTIME_DIR=/run/user/100000 \
    DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/100000/dbus/user_bus_socket \
    WAYLAND_DISPLAY=../../display/wayland-0 QT_QPA_PLATFORM=wayland \
    KELP_ADVERTISE_HOST=172.28.172.3 KELP_DEBUG_LINK=1 \
    /usr/bin/harbour-kelp >/dev/null 2>&1 </dev/null &
```

Prefix `sailjail -p harbour-kelp` to launch it the way the launcher does, inside
the sandbox:

```sh
cd / && setsid env XDG_RUNTIME_DIR=/run/user/100000 \
    DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/100000/dbus/user_bus_socket \
    WAYLAND_DISPLAY=../../display/wayland-0 QT_QPA_PLATFORM=wayland \
    KELP_ADVERTISE_HOST=172.28.172.3 KELP_DEBUG_LINK=1 \
    sailjail -p harbour-kelp /usr/bin/harbour-kelp >/dev/null 2>&1 </dev/null &
```

The variables are set on `sailjail` and do reach the app through firejail
(verified 2026-10-16: the app came up sandboxed with the real permission profiles
— `UserDirs`, `Internet`, `Base` — advertised the host's address, served the
share and logged its traffic line).

On the host:

```sh
src/tests/run-emu-share.sh --host 172.28.172.3 --qr ~/kelp-qr   # links, plus QR PNGs
src/tests/run-emu-share.sh --host 172.28.172.3 --redact         # fragment removed
src/tests/run-emu-share.sh --host 172.28.172.3 --redact --fetch # also fetch it
```

The script reads the app's own links out of the guest log, opens an ssh forward from this
host's LAN address into the guest, and prints them; if the app is advertising some other
address it says so and stops rather than print a link that cannot work. The guest port is
ephemeral, so re-run the script after the app restarts; it reuses an existing forward
when the port has not changed. `--qr` writes PNGs holding the key: treat them exactly like
the link itself, and do not leave them lying around.

`--fetch` goes on to fetch from the share through the forward, the way a recipient would —
an authenticated `/info` and root object, then two requests that must be refused — and prints
the publisher's own log line for that traffic (`kelp-probe.py`, §3.14). Nothing it prints
contains the key, so it is the quick answer to *is this share really reachable?* before a link
goes to a phone.

**Through the forward, the guest sees every peer as itself.** The port forward is dialled by
sshd *inside* the guest, so the connection arrives from `10.0.2.15` whether it came from this
host or from the phone. A traffic line (§3.14) made over the bridge therefore always names
`10.0.2.15`; that is the bridge, not Kelp.

Verified 2026-10-16 with the sealed link: an authenticated `/info`, sent from the guest
through the forward, answered `200 {"v":1,"objects":22,"files":6,"bytes":1687667}` and the
same request without a token answered `401`.

Re-verified 2026-10-16 after a restart (share *Screenshots*, 125 objects): the app logged
`bound to "10.0.2.15:43935"` / `serving on "172.28.172.3:43935"`, the script opened
`172.28.172.3:43935 -> 10.0.2.15:43935`, an unauthenticated `/info` on the host side
answered `401` (the listener is really behind the forward), and the regenerated QR PNG
decoded to exactly the link the app had minted — same pre-`#k=` text, `q=` present. The
QR was checked with `src/tests/run-emu-share.sh --redact --qr`, so the key never left
the file and the log line above it. The previous run's forward (port 45525) and its QR
were stale — the port changes with every restart.

**The host must be on a network the phone can reach.** The emulator is only
reachable *through* this host, so the phone has to reach the **host's** address —
if it cannot, the fetch just times out with "could not reach the sender — no
answer" (§2.5) and looks like an app bug. On this machine the wired LAN
(`10.42.0.0/24`) is empty apart from its router, so a phone on Wi-Fi cannot see
the host at all (a full `/24` sweep found nothing). The host's Wi-Fi was
*software*-disabled — the hardware and driver were fine — and joining the phone's
network put them on one subnet:

```sh
nmcli radio wifi on
nmcli connection up "ei hyvää päivää"   # host becomes 172.28.172.3, same as the phone
```

Enabling Wi-Fi dropped the wired connection here. With more than one network up,
the script's default `--host` follows the *default route*, so pass
`--host <wifi-address>` whenever that is not the network the phone is on.
Verified 2026-10-16: with the host on `172.28.172.3`, the phone scanned the
`--qr` code and fetched the bundle.

## 5. Driving a transfer

Two shapes, both used:

**(a) Two devices** — what was used today. On the sender: pick the entry, *Start
sharing*, then take the link (`Copy link` in the UI, or the log with
`KELP_DEBUG_LINK=1`). On the receiver: launch with `KELP_INITIAL_LINK=<link>` (or
paste it into *Open a link*) and tap *Download*.

**(b) One machine, two instances** — the original scheme, still valid: run the
sender and the receiver with different `XDG_DATA_HOME` so they have separate
stores and logs, and they will fetch over the real LAN address of the machine.

Verify a transfer with numbers, not impressions:

```sh
# receiver store: one file per object, sharded ab/<64-hex>
find ~/.local/share/harbour.kelp/harbour-kelp/objects -type f | wc -l
# the log says what it did
grep -E "round|objects are here|wrote" ~/.local/share/harbour.kelp/harbour-kelp/kelp.log
# and the content itself
sha256sum ~/Downloads/<name>
```

For a whole tree, `diff -r` the written folder against the original and compare
`sha256sum` of the two sides — that is how C2b and C3 were signed off.

## 6. Traps (each of these cost time)

- **`grep`/`pkill -f` match their own command line.** On the device,
  `ps aux | grep harbour-kelp` inside an `ssh '…'` call matches the ssh command
  itself and reports a phantom process. Ask the kernel instead:
  `for p in /proc/[0-9]*; do [ "$(cat $p/comm)" = harbour-kelp ] && echo ${p#/proc/}; done`
  and never `pkill -f /usr/bin/harbour-kelp` — it can kill your own session.
- **`pkill -x harbour-kelp` does not stop the app on the emulator.** Observed
  2026-10-16: after several launches, nine `harbour-kelp` processes were still
  running (state `S`), and `pkill -x` left them untouched — so a "fresh" run was
  actually two instances writing to the same log, which is very confusing to
  read. Kill by pid from the loop above: `... && kill -9 "${p#/proc/}"; done`.
  After the kill, re-check the count is zero before trusting a run.
- **Unload KVM before starting the emulator.** On this Linux host
  `sfdk emulator start` fails into a start-stop loop with
  `VERR_VMX_IN_VMX_ROOT_MODE` while `kvm_intel` is loaded. Ask the user to run
  `sudo modprobe -r kvm_intel kvm` first (it needs sudo; the agent does not have
  it). This is in the sailfish-os-dev skill (`environment-setup.md`) — read it
  before touching the emulator.
- **The emulator cannot be reached inbound.** It sits behind QEMU user NAT
  (guest `10.0.2.15`); the host cannot open a connection to a guest listener.
  Reach host-side services with `ssh -N -L 127.0.0.1:9999:<guest-ip>:<port>`, and
  kill such tunnels with
  `ps -eo pid,args | awk '/[s]sh/ && /9999/ {print $1}' | xargs kill`.
  The *guest* reaching a LAN host works fine. To share *from* the emulator,
  `src/tests/run-emu-share.sh` (§4.5) does the forwarding and reads the app's
  own sealed links.
- **The share's address is captured when it is shared.** The link carries the
  interface address chosen at that moment; if the device changes network within a
  session the link goes stale and the recipient gets "could not reach the
  sender" (§2.5). Nothing re-announces it mid-session; a restart re-mints the
  link from the persisted share (§3.7).
- **`KELP_ADVERTISE_HOST` lasts exactly one launch.** Any restart without it —
  including one a test helper does while putting the device back — quietly reverts
  the links to `10.0.2.15`, which is correct for the app and useless off the
  emulator. Observed 2026-10-16: after a storage-test restore relaunched the app
  plainly, a scan said *no address to fetch*. The bridge both advertises and
  forwards, so re-apply the launch line from §4.5 whenever the app is restarted,
  and re-run `run-emu-share.sh` (the port changes with every restart).
- **"No address to fetch from yet" is a *reader* that could not open the address
  block, not a link without one.** Since §3.11 the address is sealed into `q=`
  under the link's own fragment, so a build older than that finds no `l=` and
  reports no address — identical to the message for a link that genuinely carries
  none. A current build on a sealed link always shows *Fetching from <address>*
  (right or wrong) and only fails later with "could not reach the sender". Check
  the reader's build before hunting for a link-side bug.
- **A sealed `q=` block cannot be decoded on this host.** There is no
  `cryptography`/`Crypto` module here, so the address inside a sealed link is only
  readable by a Kelp build (the app, or `tst_kelpfetch`'s encode→decode→create
  path). Judge the address from the app's own `KelpServer: serving on "…"` line
  (§4.5), which is the value `publish()` seals.
- **The recipient must share a network with *this host*, not with the emulator.**
  The emulator is reachable only through the host (§4.5), so if the phone cannot
  reach the host's address the fetch times out as "could not reach the sender —
  no answer" and looks like an app bug. Here the wired LAN is empty/isolated and
  the host's Wi-Fi was software-disabled (`nmcli radio wifi on`, then join the
  phone's network). Two consequences worth remembering: enabling Wi-Fi dropped the
  wired link, and the script's default `--host` follows the default route, so name
  the address explicitly when several networks are up.
- **The emulator has no clipboard a shell can reach.** `wl-copy`/`xclip` are
  absent. `KELP_DEBUG_LINK` and `KELP_INITIAL_LINK` exist for this.
- **`open()` holds the whole tree in memory.** Fine for the sizes tested (2 MB,
  1.7 MB); a known limit for very large bundles — streaming open/write is future
  work.
- **Never record a link's `#k=` fragment.** It is the decryption key; anyone
  holding it can read the bundle. Redact it in docs, logs and chat. (Clearing a
  link out of the log is housekeeping, not revocation: the same secret is the
  share's persisted identity in owner-only `shares.json`, by design — the log copy
  is only a convenience for a device with no clipboard.)
- **In-source generated files shadow out-of-source test builds.** The app
  builds in place, so `kelpfetch.moc`/`moc_*.cpp` sit at the tree root. A test
  `.pro` whose `INCLUDEPATH` leaks the project root can make the compiler pick
  up a *stale* root `kelpfetch.moc` instead of the fresh one — this produced
  duplicate moc symbols at link. The `src/tests` project deliberately omits
  `$$PWD/../..` from `INCLUDEPATH` (with a comment saying why); if a new test
  target hits duplicate `qt_static_metacall` symbols, check for a stale
  generated file shadowing first, and remember a target switch needs
  `rm -f harbour-kelp *.o moc_*.cpp Makefile .qmake.stash` (§4.1).
- **A test that talks to a listener in its own thread must run the event loop.**
  `KelpServer` is a `QTcpServer` in the same thread as the test, so its
  `newConnection` slot only runs when control returns to the event loop. A helper
  that blocks in `waitForConnected`/`waitForReadyRead` — the obvious way to write
  an HTTP GET — never gives the listener the chance to accept, so every request
  times out with an empty reply and the failure looks like a server bug. Drive
  the socket with signals and a `QEventLoop` instead (`tst_kelpbundles`,
  `httpGet`).
- **Sailfish's Qt is 5.6.** Not 5.15: `QAbstractSocket` has no `errorOccurred`
  (the signal is a plain, overloaded `error`), `QOverload` does not exist, and
  neither does anything else from 5.7+. Select an overloaded signal with an
  explicit `static_cast<void (QAbstractSocket::*)(QAbstractSocket::SocketError)>(
  &QAbstractSocket::error)` and check the header rather than the docs when a Qt
  API "should" exist.
- **A relay refuses a client that does not offer ALPN `kelp/1`.** `KelpTls` tears
  the connection down after a handshake that negotiated anything else, or nothing
  — that is what pins the protocol version (wire spec §1.2). So a relay's HTTP side
  cannot be probed with `curl` or `openssl s_client` the way the LAN listener can:
  the client has to offer the ALPN name first (python's `ssl` can,
  `set_alpn_protocols`). The tunnel also accepts **any** certificate
  (`SSL_VERIFY_NONE`, wire spec §224: peers accept any cert because every object is
  hash-verified), which is why the relay harness's self-signed certificate is
  enough for the app's own tunnel — no pinning to work around.
- **Silica's `DialogHeader` logs a `TypeError` while it is only declared.**
  Opening a page that declares a `Dialog` with a `DialogHeader` (the QR dialog on
  *Bundle*, the confirm dialog on *Settings → Storage*) warns
  `DialogHeader.qml:175: TypeError: Cannot read property 'backIndicatorDown' of
  null` — its `pageStack` is not resolvable yet, because the dialog is not open.
  It appears on a real page push, not only under a test hook, and the dialogs work
  (both verified live); it is Silica's own binding, printed once at page load, and
  nothing to chase.

## 7. Files

`libkelp/` — pure content layer, no I/O, no networking, unit-tested:
`kelp_cbor`, `kelp_crypto`, `kelp_link`, `kelp_manifest`, `kelp_object`,
`kelp_store`, `kelp_bundle` (seal/open/walk/bundleObjects), `kelp_wire` (tunnel
frames + messages). `libkelp.pri` is the include point.

`src/` — app layer: `kelplog` (data directory + log), `kelpstore` (objects on
disk, plus `objectIds`/`objectSize`/`remove` for storage management),
`kelpbundles` (QML-facing seal/republish/unshare/link/storeUsage/pruneStore; owns
publisher tunnels), `kelpserver` (LAN listener, plus the per-peer traffic tally
that becomes the "who fetched" log line, §3.14), `kelpshares` (the shared rows on
disk, so a restart re-serves them), `kelpsettings` (the persisted preferences the
publisher acts on), `kelpfetch` (`KelpSource` → `LanSource` /`RelaySource`),
`kelpclient` (the fetch loop and the writer), `kelptunnel` (publisher's outbound
tunnel), `kelptls` (TLS 1.3 + ALPN over OpenSSL 3), `kelpqr` (the QML-painted QR
item for a share link), `harbour-kelp.cpp` (context properties).
`src/qrcodegen.{hpp,cpp}` is the vendored MIT QR encoder, with its notice in
`src/qrcodegen.LICENSE`. `src/tests/` holds the app-layer harnesses
(`tst_kelpfetch`, `tst_kelpsettings`, `tst_kelpshares`, `tst_kelpqr`,
`tst_kelpbundles`), each built and run by its own `run-*-test.sh` — plus two host
tools that are not unit tests: `run-emu-share.sh` (bridge the emulator's share to
the LAN, print its links and QR codes, optionally fetch from it) and
`kelp-probe.py` (fetch from a link the way a recipient would, without printing its
key).

`relay/` — `kelp-relay`, a separate program (not in the app package):
`relay.{h,cpp}`, `main.cpp`, `kelp-relay.pro`, `test/`. The harness
(`test/relaytest.cpp` + `run-relay-test.sh`) plays both halves against a running
relay — the recipient by hand, the publisher with the app's own `KelpTunnel` — and
prints PASS/FAIL per case. `test/certs/` holds the self-signed certificate it
generates on first run.

`qml/` — `harbour-kelp.qml` (page stack, `addBundle`), `pages/` (Bundles, Add,
Bundle, OpenLink, Settings, About), `cover/`.

## 8. Decisions already taken — don't relitigate

Name **Kelp**, app id `harbour-kelp`, scheme `kelp://`. SHA-256
content-addressing with canonical CBOR manifests; AES-256-GCM; the key rides in
the URL fragment and never leaves it. Identity is hashed, location and key are
not: `bundle_id = SHA-256` of the root manifest, location and key in the query and
fragment (`r=` repeatable relays, `q=` the publisher's own address and label sealed,
key in `#k=`). HKDF-SHA256 with a 32-zero-byte salt and info strings
`kelp/v1/content`, `kelp/v1/swarm`, `kelp/v1/relay`, `kelp/v1/link`. **Every bundle is
encrypted**; there is no public/private distinction, so swarm is a distribution
choice, not a visibility one. LAN transport is deliberately plain HTTP — the
content is ciphertext and hash-verified, Qt 5.6 cannot do TLS 1.3 + ALPN, and the
cost (an on-path sniffer learns the token, not the plaintext) is recorded in
`kelp-design.md` §3.1. A relay serves publisher tunnels and recipient fetches on
one port, told apart by the first byte, because a link's `r=` can only name one
address. Unknown bundle, unshared bundle and wrong token all answer 401 — no
enumeration oracle. UI says **folder**, never directory. Also parked, and not to
be touched: `ipfs-fileshare-PLAN.md`.
