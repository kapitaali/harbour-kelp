## 2. Bugs found and fixed in this session

These are the most valuable part of this document: none of them was caught by the
unit tests, and two of them were invisible to the emulator because of how it was
being launched.

### 2.1 A fresh install could not write anything (Sailjail data directory)

**Symptom.** On the phone, after a normal install: the app ran, showed a share,
but `~/.local/share/harbour-kelp/kelp.log` did not exist and neither did the
object store. `find / -name kelp.log` found nothing. Only
`~/.local/share/harbour.kelp/` was created, and it stayed empty.

**Cause.** The app asked for `~/.local/share/harbour-kelp`. Under Sailjail that
directory is not provisioned and the sandbox will not let the app create it.
Sailjail provisions exactly one data directory, built from the desktop file's
names — `OrganizationName=harbour.kelp`, `ApplicationName=harbour-kelp` — giving
`~/.local/share/harbour.kelp/harbour-kelp`, and hides the rest of
`~/.local/share`. The `--mkdir`/`--whitelist` pairs in the `firejail` command
line show this plainly:

```
--mkdir=${HOME}/.local/share/harbour.kelp/harbour-kelp
--whitelist=${HOME}/.local/share/harbour.kelp/harbour-kelp
```

So `KelpLog::install()` — the first thing `main()` does — could not create its
directory, and neither could the object store. Sealing had nowhere to write.

**Why it stayed hidden.** Development ran on the emulator with the app launched
from a shell, i.e. *unsandboxed*, and `~/.local/share/harbour-kelp` already
existed there from earlier runs. Deleting that directory and launching under
`sailjail` on the emulator reproduced the phone's symptom exactly.

**Fix.** `src/harbour-kelp.cpp` sets `OrganizationName`/`ApplicationName` before
any path is asked for, and `KelpLog::dataDirectory()` (`src/kelplog.{h,cpp}`)
returns `QStandardPaths::writableLocation(AppDataLocation)` — the directory
Sailjail provides, and the same path sandboxed or not. It moves an existing
`~/.local/share/harbour-kelp` into the new location once, so bundles sealed by an
earlier build keep working. Both the log and the object store use that one
function; nothing else should invent a path.

**Guard.** None in code. The check is a clean-install launch under Sailjail:

```sh
ssh -p 2223 -i $KEY defaultuser@127.0.0.1 '
  rm -rf ~/.local/share/harbour-kelp ~/.local/share/harbour.kelp
  cd / && setsid env XDG_RUNTIME_DIR=/run/user/100000 \
    DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/100000/dbus/user_bus_socket \
    WAYLAND_DISPLAY=../../display/wayland-0 QT_QPA_PLATFORM=wayland \
    sailjail -p harbour-kelp /usr/bin/harbour-kelp >/dev/null 2>&1 </dev/null & sleep 7
  ls -la ~/.local/share/harbour.kelp/harbour-kelp/'
```

### 2.2 The link could not be recovered from the log

**Symptom.** The link was searched for in `kelp.log` and was not there.

**Cause.** Deliberate: `KelpBundles` only writes the link when the app is
launched with `KELP_DEBUG_LINK=1`, because a link is a capability and its
fragment is the decryption key — logging it by default writes the key into a
plaintext file. Reasonable in general, wrong for this workflow: the emulator has
no usable clipboard, so reading the link out of the log is the *only* way to
hand it to another device.

**Fix.** Done, as proposed. *Settings → Include links in the log* is a persisted
switch, off by default: `src/kelpsettings.{h,cpp}` stores it in an INI file in
the app data directory (not `~/.config`, which the sandbox hides), and
`KelpBundles::seal` consults it before writing the link. `KELP_DEBUG_LINK=1`
still forces it on for a single run, so existing headless scripts keep working.
The switch's own description spells out that a link holds the key. Verified on
the emulator (§3.5) and covered by a restart unit test (§3.2). *(Superseded on the
default only: it now follows the build's dev-extras bundle — on in a dev build, off
and not offered in a release. §3.18.)*

### 2.3 LAN fetch always answered 401 ("the sender did not recognise this link")

**Symptom.** Pasting a valid link and tapping *Download* failed immediately with
*the sender did not recognise this link — it may have stopped sharing* (the app's
text for a 401). Meanwhile, from the same machine, `curl` with the correctly
encoded token against the same URL returned `200` and the right JSON.

**Cause.** When the fetch loop was factored behind `KelpSource`
(`src/kelpfetch.{h,cpp}`), `LanSource` was handed the **raw 32-byte** swarm token
and put it straight into the header:

```cpp
request.setRawHeader("Authorization", "Bearer " + m_token);   // raw bytes
```

The sender base64url-decodes that header value and compares bytes, so binary
garbage decodes to nothing and mismatches — a 401, indistinguishable from a wrong
token by design (no enumeration oracle). `RelaySource` was unaffected because it
puts the token in a URL path and encodes it there. `KelpClient` had done it
correctly before the split.

**Why it stayed hidden.** Every relay test stripped `l=` from the link, so the
LAN path was never exercised after the refactor, and the C2b device test predated
it. The `curl` checks passed because they used a hand-encoded token — that
mismatch between "curl works, app doesn't" is what located it.

**Fix.** `KelpSource::create` encodes the derived token before constructing the
source, and the member is now named for what it holds:

```cpp
return new LanSource(base, Kelp::Link::base64UrlEncode(swarm).toLatin1(),
                     link.lan, bundleIdText, parent);            // kelpfetch.cpp:415
```

**Guard.** `src/tests/tst_kelpfetch.cpp` (+ `tst_kelpfetch.pro`,
`run-kelpfetch-test.sh`; run it with `sfdk -c
target=SailfishOS-5.1.0.11-i486 build-shell sh
src/tests/run-kelpfetch-test.sh`). It builds a link with `l=`, goes through
`KelpSource::create` the way the client does, and asserts on the requests
`LanSource` actually sends: `Authorization` equals `Bearer ` +
`base64url(swarmToken(secret))` (43 chars for 32 bytes — raw bytes would be 32),
the paths are `/v1/bundle/<b32>/info` and `/v1/bundle/<b32>/object/<b32>`, and
the header value decodes (the sender's step) back to the token bytes. A link
naming neither address nor relay returns nullptr. Negative control verified:
with the encoding removed the test fails 4 checks; with it, 17 checks,
0 failures.

### 2.4 *Stop sharing* from the list did not stop serving

**Symptom.** Stopping a share from the **Bundles** list removed the row but left
the bundle being served: it stayed fetchable by anyone holding the link, with
nothing left in the list to stop it.

**Cause.** The long-press menu item in `BundlesPage.qml` only did
`bundlesModel.remove(index)`. The **Bundle** page's own *Stop sharing* button did
it correctly (`unshare`, then remove); the list's context-menu path predated that
and was never brought in line. A disappearing row looks exactly like a stopped
share, so nothing surfaced it.

**Fix.** The list handler now mirrors the page — `kelpBundles.unshare(bundleId)`
before the row goes, then `store.saveShares()` so the stopped share is not
restored at the next launch either. The bundle id is read *before* the removal
(`bundlesModel.get(doomed).bundleId`), because the snapshot is gone afterwards.

### 2.5 An unreachable sender was reported as a sender that "stopped answering"

**Symptom** (found by the user, not by a test). Sharing from the emulator and
fetching from another device failed with *"the sender stopped answering"*. The
emulator's own log showed it serving fine on `10.0.2.15:<port>`.

**Cause.** The emulator sits behind QEMU's *user-mode* NAT: it can dial out, but
nothing outside can dial in to `10.0.2.15`. Measured directly — the emulator
reaches the host (`200`), the host cannot reach the emulator (`curl` exit 28,
timeout). A dropped SYN is not an error the socket ever sees, so no HTTP status
came back and `KelpClient` sat until its 20 s silence deadline (`kSilenceMs`),
whose message blames a sender that had never actually been heard from. The
message was technically true and diagnostically wrong.

**Fix.** Not a reworded message on the silence deadline — a reachability probe
*before* it. `LanSource`'s first request (`begin()`) must now produce some sign
of life — response headers, or a finish carrying an error — within `kConnectMs`
(8 s); `RelaySource` must reach TLS within `kRelayConnectMs` (10 s). Any answer,
even a refusal, stops the probe, so the silence deadline keeps its real meaning
(the sender answered, then went quiet). The timeouts are deliberately generous
rather than snappy: failing a slow-but-present peer would be a worse bug than
waiting a few extra seconds.

**Met again, 2026-10-18**, reported as *"the IP isn't `172.*` but `10.*`, so it
does not work"*. The 10.x was `10.0.2.15`, so the **sender was the emulator**, and
its link had been minted by an app instance started from the guest's own app grid
rather than by `run-emu-share.sh` — whose `--relaunch` is what makes the app
advertise the host's `172.28.172.3` and opens the forward that reaches it. Nothing
was wrong with the link or the client: this section's wall, met from the other
side, and the phone's log said so plainly (`fetching … from "10.0.2.15:36131"`
then `no answer from 10.0.2.15:36131`). The cure is the script, and it only holds
for the instance it starts: **a relaunch from the app grid reverts to
`10.0.2.15`**. Now written beside the harness note in BUILD.md, because this
shape has cost a round trip twice.

### 2.6 Every row of the share list said "Offline", and a paused share could not be resumed

**Symptom** (found while photographing the list for C5.1, not by a test). Every
row of the share list said *Offline* while showing the address it was serving on,
and a row the user had paused still offered *Pause sharing* in its long-press
menu — so a pause could never be undone from the list at all. The same share's
own page (BundlePage) showed *Paused* correctly.

**Cause.** A `ListItem` is an `Item`, and `Item` has a `state` property of its
own. Inside a delegate, an unqualified `state` resolves to the delegate's own
property — which is always `""` — and **not** to the model's `state` role. Every
read of that role in `BundlesPage.qml` (`state === "seeding" ? … : …`, the menu's
label, and the branch that decides *Pause* from *Resume*) therefore read the wrong
value. Everything else reads the same field through a JavaScript object
(`bundlesModel.get(index).state` — `BundlePage.qml`, `pauseShare`,
`resumeShare`, `saveShares`, `updateShareCounters`), where the role wins; only the
delegate was wrong. The model was always right, which is exactly why a
model-level test could not see it.

**Fix.** The role is renamed `shareState`. No `Item` has that name, so the
delegate reads the model again. Nothing persisted changes: `shares.json` stores
`paused` and the state is derived from it, so no share, link or file is affected.

**Guard.** This is a view bug no unit test can reach; it was caught by taking a
photograph of the list from inside the app. The C5.1 pass now pauses a row and
photographs the list as part of its checks, so the label is evidence again.

### 3.10 Withholding the local address from links (user-requested, verified live)

> **Partly superseded by §3.11.** The `l=` below is the plaintext form that §3.11

A link is handed to whoever it is sent to — and to whoever they forward it to — and

### 3.11 Sealing the address in the link (user-requested, verified live)

The switch in §3.10 answers "should the link name me at all". The follow-up ask was
narrower: *keep sending the address, but do not send it in the clear.* Hashing cannot do
that — a hash is one-way, so a recipient could never recover a `host:port` to dial — so
the address is **encrypted** instead, under a key derived from the link's own fragment.

`Link::encode` now writes the publisher's address and the share's label into one `q=`
field:

```
q = base64url( nonce(12) ‖ AES-256-GCM(key = HKDF(secret, "kelp/v1/link"),
                                       aad = bundle_id,
                                       plaintext = CBOR{ "l": host:port, "n": label }) )
```

No new primitive: `Kelp::Crypto` already had AES-256-GCM and HKDF, and `kelp/v1/link` is
simply a fourth independent HKDF output beside content/swarm/relay. The recipient holds the
fragment, derives the same key and dials.

What that buys is worth stating plainly. The key rides in the same link, so **whoever the
link is sent to can open the block** — the address is not hidden from the recipient, who
needs it to connect. It *is* hidden from everything that sees the link without its
fragment: a redacted paste, a chat or link preview, a log, and — the case that will matter
— a browser gateway, which by convention is handed the query but not the fragment. Binding
the block to the bundle id as associated data means it cannot be lifted from one link into
another.

Compatibility is deliberately one-way. `decode` still accepts a plaintext `l=`/`n=` link,
so links and QR codes already out there keep working, and a link carrying both prefers the
sealed block. But an older *reader* finds no address in a new link and falls back to a
relay — so the phone must be updated to the new build for the LAN fast path. The link grows
from 141 to ~190 characters (`q=` is ~83), which moves the QR up about one version; it
still scans.

* `libkelp` — 312 checks (was 304). New: a sealed round-trip; the address's host part and
  the label are absent from the link text; a legacy plaintext link still decodes; a flipped

* `src/tests/tst_kelpfetch.cpp` — 37 checks (was 29): `encode → decode → KelpSource::create`
  lands on the same `host:port`, which is the recipient's whole path.
* `tst_kelpbundles` — 22 checks, unchanged in count; its helper now decodes the link to ask

* Live, on the emulator: the app logged `KelpServer: bound to "10.0.2.15:45525"` and

### 3.12 Storage management: seeing and reclaiming what nothing needs (design §12.7, verified live)

The last open design question with teeth. Every seal and every fetch writes objects into one
deduplicated store and **nothing ever deleted from it**; the count and size were visible on the
About page, but there was no way to reclaim a byte. On this device the store had already drifted
from 22 to 33 objects — the difference being what earlier fetch tests left behind.

The obstacle is that "unused" cannot be answered per bundle. The store is one pool with dedupe,
so an object may belong to several shares at once, and there is no reverse index from an object
to the manifests that name it (the graph points down, not up). The only sound definition is
global: *the objects every share on this device reaches, walked in full*. Everything else is
either what a fetch left behind or what a share that is gone no longer needs. Downloads
themselves are ordinary files in `Downloads`, so their cached objects are disposable — removing
them costs a re-download, not the content.

That walk is `Kelp::bundleObjects(store, key, rootId, &ids, &error)`, new in `libkelp`. It is the
same traversal as the fetch planner, with two deliberate differences. It **notes an id as it
visits it** rather than only when it is absent, so a whole bundle enumerates instead of returning
an empty "missing" list. And it is **strict about manifests**: every manifest must be present and
must open with the key. That is the safety property the whole feature rests on — the entries under
an unreadable manifest are unknown, so a list that cannot account for them must not be used to
decide what is unreferenced. Data objects are only *named* by their manifests, never read, so a
bundle whose chunks have holes still enumerates completely.

The app side needed only two calls. `KelpBundles::storeUsage(shares)` returns total objects/bytes,
the subset the shares need, and the difference; `pruneStore(shares)` deletes exactly that
difference. Both take the share rows **from the UI** (`store.bundlesModel`) rather than reading
`shares.json` back, so "in use" is exactly what the device is really serving. If any row cannot be
walked, both refuse and delete nothing — a share that cannot be read must never have its objects
mistaken for junk. The store gained `objectIds()` (walks the sharded tree; a half-written `.tmp`
never passes the id-length check), `objectSize(id)` and `remove(id)`.

Settings → **Storage** shows the breakdown and offers **Remove unused objects** behind a confirm
dialog, enabled only when there is something to remove. The wording is honest about what it
costs: the leftovers are a cache, and anything fetched from a link again is downloaded once more.

Verified:
* `libkelp` — 345 checks (was 312). New: a sealed bundle lists exactly the store's contents
  (every manifest and every chunk, nothing invented); no id twice; the wrong key fails rather
  than returning an empty list; dropping a *data* object leaves the listing complete while
  dropping a *manifest* is refused; a missing root or a stub id fails.
* `tst_kelpbundles` — 54 checks (was 22). New: a sealed share reports every object in use and
  zero unused; a stray object is reported as the only unused one; clean-up removes it and every
  object the share needs survives, root included; a second clean-up removes zero and succeeds;
  and a share whose stored key no longer opens its manifests makes *both* calls refuse, leaving
  the store — stray and all — untouched.
* Live, on the emulator, through the real Settings page (created from the installed QML):
  `usage-before`: 33 objects, 3.6 MB, in use 22 (1.6 MB), unused 11 (2.0 MB). `prune removed=11
  freed=2136892`. `usage-after`: 22 objects, in use 22, unused 0. The share's 22 objects were
  byte-for-byte the same set afterwards, and the app kept serving it. The store was tarred before
  the run and restored afterwards, so the device was left exactly as it was found.

### 3.14 The publisher's own view of a fetch (verified live)

The debugging session in §3.13/§2.5 exposed the gap this closes. The server logged **nothing per
request**: a recipient that fetched all 125 objects and one that never arrived left exactly the
same trace in the publisher's log — none. The app has a logging feature precisely so a problem
can be diagnosed from the device, and the half that was being diagnosed was invisible in it. The
only way to know a fetch had happened was to ask the person holding the phone.

`KelpServer` now tallies what each peer asks for (`Traffic`, `src/kelpserver.{h,cpp}`):

| counter | what it is |
|---|---|
| `requests` | authenticated `/info` calls — the client makes one at the start of every fetch, so this is *fetches started* |
| `objects` / `bytes` | objects actually written out, and their size as stored (ciphertext) |
| `refused` | `401`s: a link the server does not know or a token that did not match |
| `bundle` | the name of the last share involved, so the line reads as something |

The tally is keyed by **peer address, not address:port** — every request arrives on its own
connection (`Connection: close`), so a port would make each object look like a new peer. It is
written as **one line per peer**, about five seconds after that peer's last request, from the
sweeper that already tidies half-open connections; nothing logs per object. That keeps the
useful signal (did anyone fetch, and did they get all of it) while a busy share cannot turn into
a log flood, and a run of failed attempts costs one line with a count rather than one line each.

```
KelpServer: "10.0.2.15: 1 fetch(es) started, 1 object(s), 102 byte(s) of \"Screenshots\"; 3 request(s) refused"
```

Unlike links, this is **not** behind a setting: a traffic line carries no key, only counts, byte
sizes, a share name and an address, in the publisher's own local log. The share name had to be
added to `KelpServer::share()` for it — the server was never told one — which is why the line can
say *"Screenshots"* instead of *"a bundle"*.

* `tst_kelpbundles` — **79 checks** (was 54). The new test drives the **real listener over a real
  socket** (a hand-written HTTP GET): an authenticated `/info` answers 200 and the tally shows

  answers 200 and the tally shows exactly one object and exactly the bytes the body carried; an

`src/tests/kelp-probe.py` (new) is the probe: it reads the publisher's log on stdin, picks up the
newest link, derives the bearer token the way `libkelp` does (HKDF-SHA256, 32 zero-byte salt,
info `kelp/v1/swarm`), and makes those four requests. The `#k=` fragment **is** the key, so it is
parsed and never printed — the output is status codes and sizes only, safe to read or paste. It
checks reachability, authorisation and that objects leave the device: everything except the
recipient's own crypto. `run-emu-share.sh --fetch` runs it against the forward and then prints
the publisher's line for that traffic, so a share can be checked *before* it goes to a phone.

**This covers the LAN path only** — the relay half is §3.15.

Two traps this cost, both recorded in §6: the listener lives in the same thread as the test, so a
test that blocks in `waitForConnected`/`waitForReadyRead` is never accepted — the event loop has
to run; and Sailfish's Qt is **5.6**, where `QAbstractSocket` has no `errorOccurred` signal
(that is 5.15) and `QOverload` does not exist (5.7), so the socket-error overload is selected with
an explicit cast.

### 3.15 …and the same for the relay path (verified in the relay harness)

The gap §3.14 left open was the *cross-network* half — the one with the most ways to fail, since a
fetch there needs the publisher's dial-out to have survived, TLS to have come up, the relay to
have forwarded the WANT, and the object to have been found in the store. `KelpTunnel` now keeps
the same account, per tunnel rather than per peer (the relay multiplexes recipients, so a per-peer
count is not knowable from this side):

| counter | what it is |
|---|---|
| `wanted` | WANT frames: objects a recipient asked for through this tunnel |
| `objects` / `bytes` | DATA frames sent, and their size as stored |
| `rejected` | REJECTs: wanted, but not held here — a stale share, or a bug worth chasing |

It is reported the same way, from a single-shot timer that every WANT restarts, so it costs
nothing while idle and lands about five seconds after a transfer stops. It is also reported on
teardown — a tunnel that drops, or rotates to the next relay, writes what it served first, so a
transfer interrupted by a reconnect is still accounted for and the line names the relay it was
actually on.

```
KelpTunnel: "127.0.0.1:9643: 2 object(s) wanted, 1 served (27 byte(s)), 1 not held of \"relay test\""
```

**The relay harness now runs this code instead of a stand-in.** `relay/test/relaytest.cpp` used
to hand-write the publisher's half of the wire protocol — which meant the relay was tested
against a re-implementation, and a bug in the app's own framing or state machine could not be
caught by it. It now builds the app's real `KelpTunnel` on a real `KelpObjectStore` and lets it
register and serve, so the same code the device runs is what the relay answers.

Verified: `relay/test/run-relay-test.sh` — **6/6 ALL PASS** (was 4), with two new cases:

```
PASS tunnel tallied the transfer — wanted=2 served=1 bytes=27 notHeld=1
PASS tunnel reported itself and reset — wanted=0 served=0
```

The first pins the count against what the harness actually asked for: two objects wanted (the one
held here, and one it does not have), one served, its 27 bytes, one not held. The second is the
proof that the log line really ran — reporting resets the tally, so an empty tally afterwards is
the evidence. The line above is the app's own `qInfo`, printed by the harness
(`QT_LOGGING_TO_CONSOLE=1`, which the run script now sets for both halves).

Scope, stated plainly: this was verified **in the harness**, which is a real relay over real TLS
1.3 with the app's own tunnel as the publisher — not re-run live on the emulator today. The relay
path itself was verified live during C3, and what is new here (the tally and its report) is shared
with the LAN path, whose live check is §3.14. Nothing on the device is configured with a relay
(`Kelp: relays =`), so a live pass would need one running and reachable first.

### 3.16 Pausing a share without deleting it (user-requested)

The only control a share had was *Stop sharing*, and it is destructive: it stops serving **and**
removes the row, after which Storage clean-up may reclaim the objects. That is right for "I am done
with this", but it is the wrong shape for "quiet for a while" — and it is the wrong shape outright
for background serving, where the app keeps serving after the window is gone and the user needs a
way to silence one bundle without dismantling it.

So a share can now be **paused and resumed**:

- **Pause** stops serving — the relay tunnel is closed and the bundle is removed from the LAN
  listener — but keeps the row and every object. The share keeps its identity (bundle id + secret),
  which is what makes it resumable. Its link is dropped with the address, because the address is
  only good while it is being served.
- **Resume** serves it again exactly as a restart does: `republish()` re-advertises on the LAN,
  reopens the relay tunnel and mints a fresh link. A link handed out before the pause starts
  working again (its relay half, if it had one, never moved; its LAN half is a new address).
- **Stop sharing** is unchanged: it stops serving *and* deletes the row.

`paused` is persisted in `shares.json`, so a share the user silenced stays silent across a restart
rather than coming back serving itself. (With no background service yet this is mostly a promise
for later, but the intent is the same either way.)

**Where it lives.** `KelpBundles::pause()` and `KelpBundles::unshare()` are now two names for one
act — the serving stop — factored into a private `stopServing()`; `unshare()` logs *no longer
serving*, `pause()` logs *paused - objects kept*, and `republish()` is the resume. In QML the store
owns `pauseShare(index)` / `resumeShare(index)`, so the list menu and the Bundle page share one
implementation instead of each editing the model. A small `sharesRevision` counter on the store is
bumped whenever a row changes in place, and `BundlePage.entry` reads it, because a `ListModel`
`get()` returns a snapshot and would otherwise not notice the `setProperty()` that pause/resume do.

**Verified.**

- `tst_kelpbundles`: **93 checks, 0 failures** (was 79). Two new sections drive the real listener —
  a fetch is answered while serving, *refused with the same 401 a stranger gets* after
  `pause()`, and answered again after `republish()`; and the store still contains the root object
  afterwards, with `storeUsage()` still calling the paused share's objects **in use**, so a
  clean-up cannot mistake a pause for a delete.
- Live on the emulator, both restore paths: a plain restart restored and served the saved
  *Screenshots* share (`KelpBundles: restored …`, `KelpServer: serving on …`); with `"paused": true`
  added to the row, the next launch logged `restoreShares: leaving "Screenshots" paused` and the
  list still counted **1** — and no `serving on` or `restored` line at all, i.e. the listener never
  bound, which is what "not served" means here. No QML warnings on either launch.
- The in-session pause/resume *buttons* call that same `pause()` / `republish()`, so they are
  exercised by the unit checks above; only the UI wiring itself was not clicked by hand. The
  emulator was left as it was found (row restored, share serving, no test files, bridge closed).

**The cover's play/pause is now the same pause.** The cover action used to toggle an inert
"background seeding" property — one of the placeholders — which read as a pause that did nothing.
It now pauses *every* share, or resumes them all (`pauseAllShares()` / `resumeAllShares()` on the
store, which are just the per-share functions in a loop), so the app-wide control and the
per-share one cannot drift apart; the icon follows the real state (pause while anything is not
paused, play otherwise). It binds to the store's `servedShares` / `pausedShares` counters, not to
a walk of the model. *Share in background* in Settings stays the placeholder it was — it is about

### 3.17 Serving survives leaving the foreground (verified live)

The design called background serving "a design decision rather than just code" (§12.8), and it is
two questions, not one: *does* serving keep working when the window is gone, and *should* it.

The first has a plain answer on this platform. Sailfish keeps a backgrounded app genuinely alive —
the cover view is a live process, not a snapshot — so serving already continued while Kelp was on
its cover; nothing in the app stopped it. What was missing was the request not to be *ended*, and
the platform provides exactly that: `Nemo.KeepAlive` (base-image `libkeepalive`, a Harbour-allowed
QML module — `references/allowed-apis.md`). Kelp now holds it while something is really being
served **and** the user asked for background sharing, and releases it otherwise — an idle app has
no business resisting power management. That is all the battery story this version can honestly
tell; Wi-Fi-only and low-battery gating are still open (§12.8).

The second question is one the old label answered wrongly. *"Keep seeding after the app is closed"*
was never achievable: a Harbour app cannot ship an always-on service (that is a systemd user
service, OpenRepos territory). Closing Kelp ends serving, and the Settings text now says so instead
of promising otherwise.

Verified live on build `20261017-093223`:

- `KeepAlive: background serving on (setting on, 1 served)` at startup, and a state logger
  reporting `Kelp: application state = active`.
- Backgrounded for real by bringing another app to the front — `invoker --single-instance
  --type=silica-qt5 /usr/bin/jolla-settings` over ssh, which needs no gesture (§4.6). The log then
  showed `Kelp: application state = inactive`, so the platform does report the state Kelp cares
  about.
- With Kelp on its cover, a recipient-style fetch through the host forward answered exactly as it
  does in the foreground: `/info` and the root object `200` with the right token, `401` with none
  and with a wrong one, and the publisher logging
  `1 fetch(es) started, 1 object(s), 102 byte(s) … 3 request(s) refused`. **Serving does not depend
  on the window being in front** (§4.5).
- No `WARN` or `ERROR` for the whole launch, checked in `kelp.log` (§6).

Two things were deliberately *not* built, recorded so they are not re-litigated:

- **A bottom `PushUpMenu` with a "Share in the background" item** (the user's suggestion, to make
  the setting reachable without the emulator's flaky bottom-edge swipe). Dropped — the user would
  rather use the real device's gesture, and a menu item could only have flipped the setting, since
  **an app cannot send itself to the background**: the only lipstick object that looked promising
  (`/WindowModel`) is a read-only item model (`revert`/`hasIndex`/`rowCount`/…), `org.nemomobile.lipstick`
  exposes no minimize call, and backgrounding an app is the platform's gesture by design. A Harbour
  app reaching into Lipstick's private D-Bus to fake it is not a thing to ship.
- **Persisting the *Share in background* switch.** It stays a plain QML property that resets to on
  at each launch, like its *Wi-Fi only* and *Allow peer swarm* neighbours — the three are still
  placeholders in that respect (§9). `KelpSettings` is where a preference the app must remember
  goes, and this one was not judged worth a setting yet (the default, on, is also the useful one).

app left running (on its cover, brought there for the test), no test files or leftover RPMs on the
guest.

### 3.18 The dev-extras bundle: links in the log by default, but never in a release (user-requested)

The user's first ask was to turn *Include links in the log* on by default. Their second was
better: put it in a **feature bundle** — a named group of development/testing conveniences that a
release build turns off — so the convenience exists while developing and cannot ship by accident.

That bundle is `src/kelpbuild.h`: `KelpBuild::devExtras()`. It is a build-time value, and it is off
unless the build asks for it, so the safe answer is the one a build gets when nobody said
otherwise. `KELP_DEV_EXTRAS=1` at build time defines `KELP_DEV_BUILD`; the RPM spec sets it while
developing (`%define kelp_dev_extras 1`) and a release sets that to 0. A build that asks for
nothing — a bare `qmake` — is a release. QML sees the bundle as one `kelpFeatures` context property
(a map of flags, today just `kelpFeatures.devExtras`), so the next dev-only feature needs no new
context property, and every launch records which build it is:
`Kelp: build mode — dev extras on|off`.

Three things follow, and they are the whole change:

- `KelpSettings::includeLinksInLog()` defaults to the bundle: on in a dev build, off in a release.
  The setting is still a setting — what the user picks is what persists (both test runs below write
  it and read it back off disk).
- The guarantee that matters is at the point of use: `linksInLog()` in `kelpbundles.cpp` returns
  false in a release build whatever the preference or the environment says. That closes the hole a
  default alone would leave (a `settings.conf` carried over from a dev build), and it makes
  `KELP_DEBUG_LINK` part of the bundle too — **a release build never writes a link into the log**,
  full stop.
- *Settings → Include links in the log* is **not shown** in a release build
  (`visible: kelpFeatures.devExtras`): an app should not offer a switch that cannot work.
  *Clear log*, the rest of Diagnostics and the About page stay as they are — the debugging log is
  not dev-only (§1, §7).

Verified. The preference test is written so the default it checks *is* the build's
(`CHECK_EQ(settings.includeLinksInLog(), KelpBuild::devExtras())`), so it is meaningful in both
configurations, and it was run in both — the test projects share the switch through
`src/kelpbuild.pri`, so a test build is what its environment asks for, exactly like the app:

```
tst_kelpsettings, KELP_DEV_EXTRAS unset : 24 checks, 0 failures
tst_kelpsettings, KELP_DEV_EXTRAS=1     : 24 checks, 0 failures
tst_kelpbundles,  KELP_DEV_EXTRAS unset : 98 checks, 0 failures
tst_kelpbundles,  KELP_DEV_EXTRAS=1     : 98 checks, 0 failures
```

`tst_kelpbundles` gained a section that installs a Qt message handler and proves a link is offered
to the log only when the build allows it, with the switch on *and* off (93 → 98 checks; the handler
also keeps the link out of the test's own output). That a run really was the configuration it
claims was checked out of band, in the generated Makefile: `KELP_DEV_BUILD` is present for
`KELP_DEV_EXTRAS=1` and absent otherwise.

Both builds were then deployed to the emulator and launched plainly — no environment overrides,
same saved share, whose restore mints a fresh link on the exact line that writes one to the log:

```
release build (spec: %define kelp_dev_extras 0)
  Kelp: build mode — dev extras off
  KelpBundles: restored "Screenshots" -> 125 objects, 26 files, 23257981 bytes
  kelp:// lines written to the log: 0

dev build (spec: %define kelp_dev_extras 1)
  Kelp: build mode — dev extras on
  KelpBundles: restored "Screenshots" -> 125 objects, 26 files, 23257981 bytes
  KelpBundles: link "kelp://…"          (one line — never quoted here, it holds the key)
  kelp:// lines written to the log: 1
```

Neither launch wrote a `WARN` or `ERROR`, and neither had a `settings.conf` on the device, so what
was tested was the default and not a stored value. Nothing about the dev build is read from the
device's state: the same rows, the same object store, only the binary differs.

The switch's own visibility needs a screen, so the Settings page was opened on the emulator through
a temporary hook in the installed `harbour-kelp.qml` (it pushed the page at startup; removed
afterwards, and the installed file was checked back to the tree's own digest, md5 `cab230c9…`). The
page rendered — Sharing, Swarm, Relay, Storage all there — and the log held no QML error beyond
Silica's own known `DialogHeader` warnings, which is the point: a `visible: kelpFeatures.devExtras`
binding that could not resolve would have logged a `ReferenceError` and left the switch wrongly
showing in a release build. The Diagnostics section sits below the fold of the capture the host
could take, so the switch itself was not photographed — the binding is proven to evaluate, and
`devExtras` is `true` in a dev build (the build-mode line above).

Two traps, the second met while making this change. First: `make` cannot see `-D` flag changes and
the bundle *is* a define, so flipping `%define kelp_dev_extras` and rebuilding incrementally leaves
a stale `devExtras()` behind — the build is quietly still the mode it was last compiled as.
`harbour-kelp.pro` now touches every file whose compilation depends on a define, not just `main()`.
Second, seen for real: `%qmake5_install` is a `make install`, and a `make` that finds a stale
Makefile regenerates it by re-running qmake — in a shell where the spec's `%build` export no longer
applies. The aarch64 build here printed the switch message **twice**, `on` then `off`, because its
`.pro` was edited while it ran; the `off` was that regeneration, which happens after the objects
have been compiled (that run's binary was unaffected, but nothing about it said so — only the
single-message clean rebuild settled it). Every build in this section was made from a clean tree
with the inputs left alone (§4.1).

The committed spec is set to 1 — while developing. Making a release is one line:
`%define kelp_dev_extras 0` (README, *Development builds*).

### 3.19 Build documentation, and the shared-page preview designed (user-requested)

Two requests, no code changed.

**How to build, written down once.** The build knowledge was spread across the README, §4.1
here and the handoff, each with half a recipe. `META-INF/BUILD.md` is now the canonical build
and test document — the two targets, the clean rule that switching target *or* changing a
define needs, the dev-extras dev/release switch and what to check after flipping it, what a
build produces (including that the About page's "build id" is a UTC *timestamp*, because the
SDK engine has no git), every suite with its expected count, the checks before committing,
deploy and run, and the traps that have actually cost time. README, §4.1, §7 and the handoff
now point at it rather than repeating fragments of it.

The command that document tells a future agent to use for tests did not exist, so it does now:
`src/tests/run-all-tests.sh` runs libkelp, the five app suites and the relay harness in one
build-shell call, one line per suite, and keeps going past a failure instead of stopping at
the first. Verified in both bundle modes — `345 + 37 + 24 + 24 + 9 + 98` checks and the relay's
`ALL PASS`, twice — and the script prints which mode it was asked for, so a run cannot be
mistaken for the other one.

**The shared-page preview, designed.** The user's idea: send a `kelp://` link and the
recipient's app opens a browser and serves the html+js *from the sender's phone*. Written up as
`kelp-design.md` §5.1, with the relay gateway moved to §5.2 and the entry-document convention
into §5.3. It turned out to be a different feature from C4 rather than a variant of it, so the
milestone split into **C4a** (preview, app-hosted) and **C4b** (gateway, relay-hosted): opposite
trust models, almost no shared work.

The one fact that decides the shape: a browser **cannot** decrypt from the sender.
`crypto.subtle` exists only in a secure context (`https://` or `localhost`), and the LAN path
is deliberately plain `http://` on a private address (§3.1), so a page loaded from the sender's
phone has no AES-GCM and no HKDF. The recipient's app therefore decrypts and re-serves on
`127.0.0.1`, under a random token path, and the loopback origin becomes the security boundary:
a CSP that forces the page offline and same-origin, `no-store`, `nosniff`, no bridge to the
app, an ephemeral profile, and a first-preview confirmation that says plainly that this runs
the sender's code. That confirmation may be remembered per bundle id because ids are content
addresses — the same id is the same immutable bytes, the one place immutability pays a security
dividend for free. The server itself is a resolver (path → chunk list → bytes, `Content-Type`
from the manifest's own `mime`, `Range` as a contiguous object range while chunking is fixed),
it lazily fetches through the existing `KelpSource`, and it is testable with no browser at all.

Two ways to open it are specified — hand the URL to the system browser (recommended first: no
new dependency, and the CSP still holds) or an embedded `Sailfish.WebView` (stronger leash,
heavier, QtWebEngine under Sailjail unproven) — and §5.2's gateway is now a *loader* that mounts
the same entry document, with its "a malicious relay can serve a loader that steals the key"
caveat written down rather than implied. Nothing is implemented; §5.1's last section is the
plan.

The user then asked whether the same link could open an **anonymous chat** that stores nothing;
the answer is *yes in transport, no in content model* — a sibling protocol, now sketched as
`kelp-design.md` **Appendix B** (`kelpchat://`, rooms in RAM, messages as objects, a relay that
fans out what it cannot read, no scrollback and no offline delivery, and "anonymous" honestly
scoped to content rather than participants). It is explicitly **parked**: not a milestone, and
not to be started or designed further until the app itself is otherwise finished and released.
What the question did produce is the honest comparison in B.2 — Kelp fits a chat's transport
almost unchanged and its content model not at all — which is worth having written down even if
rooms are never built.

### 3.20 C4a: the shared-page preview, built ("we will implement the servable html thing")

The user asked to continue with C4 and confirmed the servable-HTML half is in scope, so §5.1
went from design to code. Off-device, the whole path is now tested; the on-device browser pass
has not been done yet (the emulator takes no input injection).

**What is in the tree.**

- `libkelp/kelp_web.{h,cpp}` — the §5.3 convention as pure code. `page()` (which file the bundle
  offers, with the candidates when it does not choose), `resolve()` (bundle path → file or
  directory, **manifests only**: a data object is never read), `chunkRange()` (byte range →
  contiguous chunk range) and `mimeType()` (extension table; the manifest's `mime` wins if a
  sender ever recorded one). Added to `libkelp.pri`, so libkelp's own suite builds it.
- `src/kelppreviewserver.{h,cpp}` — the loopback server of §5.1: `127.0.0.1` only, an ephemeral
  port, one session per open bundle behind a 32-byte hex token, `GET`/`HEAD`, the CSP +
  `nosniff` + `no-referrer` + `no-store` headers on **every** response, `Range: bytes=a-b|a-|-n`
  (multi-range and malformed requests ignored, `416` past the end), the directory rules (`/sub/`
  → `sub/index.html`; `/sub` → `301 /sub/`), `404` for an unknown token or any path not in the
  manifests, `503` for anything the store cannot answer yet, chunks decrypted straight to the
  socket (never buffered whole, never written anywhere), and a session dropped after 30 minutes
  idle. It takes a `Kelp::ObjectStore*`, not the on-disk store, so its tests can use the memory
  store.
- The app seam — `KelpBundles::pageInfo/previewPage/endPreview/previewSessions` (plus
  `previewSessionsChanged`), `harbour-kelp.cpp` creating the server and handing it over, and
  `KeepAlive` now held while a preview is live as well as while a share is served.
- The first UI — a **Web page** section on a bundle's own page (BundlePage), shown only when the
  bundle has one, with *Open in browser* → `Qt.openUrlExternally` (route B of §5.1). No menu:
  the section is where the page already lists the share's link and buttons. The page's identity
  is asked once on page open (`pageInfo`) and logged when it fails.
- Tests — `src/tests/tst_kelppreview.{cpp,pro}` + `run-kelppreview-test.sh` (202 checks: the page
  convention, path resolution, chunk ranges, content types, a real socket at every status, the
  lazy/manifests-only store, holes, the on-disk store) and a new `tst_kelpbundles` section
  through the real `KelpBundles` seam (+28 → 126). `run-all-tests.sh` now runs six app suites.

**Two design points the code settled, both now written into §5.1.**

*`404` and `503` are different answers.* `Web::resolve` returns false **with** an error when a
manifest it needs is missing or unreadable — the bundle is not all here yet — and false with
**no** error when the path simply is not in the manifests. The server turns the first into
`503` and the second into `404`. That distinction is what makes "manifests first, data lazily"
real: `page()` reads the manifests of every file (to know which are HTML) but no data object at
all, so a store holding only the manifests can still be previewed, serve the page's shape, and
say honestly `503` for content it has not fetched. `tst_kelppreview` proves it by building a
manifests-only store from a full one and watching `/` go `503` → copy one file's chunks → `200`
while `/style.css` stays `503`.

*The trailing slash is a fact about the request, not the path.* The first version dropped empty
URL segments, so `/sub/` resolved to the path `sub` with no slash and redirect-looped forever.
Found by the suite (`301` where `200` was expected), fixed by passing `rawTarget.endsWith('/')`
into the resolver, and pinned by `/sub/`, `/sub`, and `/images` (a directory with no
`index.html`, which redirects like the others).

**Small traps, for the record.** `tst_kelpbundles` had no `show(const QByteArray&)` in its
check helper (it had never compared byte arrays) — a `QString` conversion made every such
comparison ambiguous, fixed by adding the hex overload. `QTemporaryDir::filePath()` is Qt 5.9+;
Sailfish's Qt 5.6 has only `path()`. And `KelpBundles::seal` wraps a picked folder under its
basename, so a sealed `…/site` is previewed at `site/index.html` with the URL root at `site` —
correct, and twice written wrong in the new test first. The app link failed once with
`kelp_bundle.o: file format not recognized` because the previous build had been aarch64: the
`Makefile` was up to date, so the stale object was reused. The clean rule in `BUILD.md` is the
fix, and it is worth remembering that the failure looks like corrupt source rather than a
stale target.

**Verified.** All seven suites, both bundle modes:
`345 + 37 + 24 + 24 + 9 + 126 + 202` checks and the relay's `ALL PASS`, twice; the i486 app
build clean afterwards (only the known `libQt5Network`/`libcrypto` linker warning). Nothing in a
log or a doc holds a token or a `#k=` fragment: the preview URL is a capability and
`KelpBundles` writes it only under the same gate a link is written under (`linksInLog()`),
which a release build never has.

**On the emulator (real tool output).** A temporary startup hook stood in for the tap the

### 3.21 C5.1: webpage shares, the publisher's half (design §5.5)

- `libkelp/kelp_cbor.{h,cpp}` — a `Bool` type (`0xF4`/`0xF5` only; `0xF6`/`0xF7` and any

### 3.22 C4a.2: view-only webpage links — the recipient's half (design §5.5)

**The seams it moved.**

- `KelpPreviewServer` no longer owns a store. `using StorePtr = QSharedPointer<Kelp::ObjectStore>`;
  `open(store, …)` / `openEntry(store, …)`; each `Session` holds its own reference, so a session
  cannot be left serving a store that something else freed. The app hands over the app store with a
  deleter that does nothing — it borrows the *store* while sharing the *reference*. One listener
  still serves both kinds of page, a share's own and a received one.
- `KelpClient` gained the second ending: `fetchForViewing()` (same walk, `MemoryStore` instead of the
  app store, nothing written), `openPageView()` (finds the page, opens the session, returns

  `activeStore()` used by the walk, and the ceiling — `32 MiB`, checked against `/info`'s claim
  before a byte is fetched and again against what actually arrives. `reset()` releases the client's
  own reference and any session keeps its own. Its constructor now takes a `Kelp::ObjectStore *`
  rather than the concrete `KelpObjectStore *` — it only ever used the interface, and that is what
  lets the tests hand it a `MemoryStore`.
- `KelpBuild::linksInLog(const KelpSettings *)` moved out of `kelpbundles.cpp` into the dev-extras
  bundle, so the publisher and the receiver answer "may a capability URL be logged?" from one place
  instead of two that can drift.
- QML: `OpenLinkPage` reads the new `parsed.page` and branches — no *Save to*, no *Download*, one
  **Open in browser**, a line saying the page is only looked at, and a Done panel that reads
  *Opened in browser* / *Nothing was saved — a page shared with you is only looked at.* KeepAlive's

### 3.23 C4a.2 on the C2: a real browser (the last open verification)

The emulator has no browser, so the receive side's browser end could only be proven there with
`curl` (§3.22). The user carried the aarch64 RPM to the C2, opened the emulator's `web` demo share
from it and pressed *Open in browser*. The first line of evidence is the publisher's own, from this

```
2026-10-18 08:36:59.099 INFO  KelpServer: "10.0.2.15: 1 fetch(es) started, 4 object(s), 55969 byte(s) of \"web\""
```

That is a *complete* fetch — every object, every byte — which `kelp-probe.py` never does: it asks for
`/info`, then only the root object, then two requests that must be refused (§4.5). So the line could
only come from a real `KelpClient` on the far side of the forward: the phone. (The address reads
`10.0.2.15` because the forward is dialled by `sshd` inside the guest, so every peer looks local —
§4.5.) The user's own report: *"open in browser works!"* — the page came up in the C2's browser and
nothing appeared in Downloads.

**What it looked like, and why.** The demo page is one `index.html` (55670 bytes) saved from a
website, and it expects two things from the internet:

```
https://cdn.tailwindcss.com                (the CSS framework)
https://unpkg.com/@phosphor-icons/web      (an icon font)
```

The preview's CSP is `default-src 'self'; img-src 'self' data:; media-src 'self'; style-src 'self'
'unsafe-inline'; script-src 'self' 'unsafe-inline'; connect-src 'self'; frame-ancestors 'none';
base-uri 'none'` (§5.1), so every off-origin subresource is refused and the page rendered
**unstyled**: the content and its own links were there, the framework was not. That is the §12.11
recommendation working — the recipient's device never contacts a third party the sender picked, and
a CDN request is exactly how the sender's page would learn it had been opened. Note what is *not*
blocked: an ordinary link to another host still navigates when clicked, because none of those
directives covers navigation. For a demo that shows off the feature, the answer is a self-contained
page (inline `<style>`, `data:` images), not a loosened CSP; an explicit per-page "let this use the
internet" switch is a design question, recorded in §12.11, and belongs with the sender's declaration
and the reader's consent rather than in the preview.

**Nothing was written — anywhere.** Downloads is untouched, and it is not a case of "saved somewhere
else": a view never has a destination. The emulator run pinned it (`files=0 bytes=0 destination=''`,
and the app's object store byte-identical before and after, §3.22), and the C2's copy of the same
code takes the same path. On the phone it can be checked from the app itself: **Settings → Storage**
should show the same object count and size as before the view, and the bundle list gains no row.

**Cause, in two halves.**

*The page.* `KelpClient` outlives the QML page that drove it, so a page opened
later finds the last visit's finished view still sitting in the client: `phase` is
`"done"`, and the page's Done panel and its *Open in browser* button both read
that phase. A brand-new link was therefore presented as already opened, and
pressing the button took the "already open" path instead of fetching.

*The URL.* `openPageView()` returned its cached `m_viewUrl` whenever it had one,
without asking whether the session behind it still existed. After the sweep it
did not, so what it handed the browser was dead.

**Fix.** A fetch belongs to the link that asked for it, and both halves now say so:

- `KelpClient` keeps `m_link` — the trimmed link text each fetch is about — and
  answers `isHandling(link)`, so the QML page can ask *"is what I see in this
  client mine?"* for a save exactly as for a view.
- `OpenLinkPage.qml` presents a finished fetch (the Done panel, *Open another
  link*, the *Try again* label) and takes the "already open" path only when the
  client is handling **this** page's link. A failure is gated the same way, or a
  new link arrives wearing the last one's complaint.
- `openPageView()` asks `KelpPreviewServer::has(token)` before handing a URL back.
  If the session is gone the memory store is still here, so it mints a fresh
  session for the same page instead of handing out a dead URL (a second press
  therefore also recovers a page whose session expired while it was being read).
- The unknown-token `404` body now says what a reader can do about it:
  `no such preview: it has ended, or the address is wrong. Open the link again from Kelp.`

### 3.28 K2: a serving policy that stops serving politely (verified live)

**What was wrong.** §12.8's open half: the app held `Nemo.KeepAlive` while it served, but
`wifiOnly` and a low battery did nothing at all — the switch was a placeholder and the
battery was never read.

**The rule, in `libkelp` so it is testable and has one home.** `Kelp::Policy::servingBlock()`
is a pure function of `(wifiOnly, metered, power)`. Metered means **the device's only
usable connection is cellular**: an interface counts if it is up and carries an address
that is neither loopback nor link-local, and it is cellular if the kernel does not mark it
wireless (`/sys/class/net/<if>/wireless`) *and* its name looks mobile (`ccmni*`, `rmnet*`,
`wwan*`, `pdp_ip*`, `ppp*`). An unclassifiable name is **unmetered on purpose** — guessing
"metered" would stop serving on a wire or a VPN. Battery blocks below 15% while not
charging; "Charging" and "Full" count as charging, an unreadable battery as unknown and
never blocks. `tst_kelp` went 393 → 420 checks with the truth table (metered off/on,
charging, exactly at the threshold, below it, two Wi-Fi interfaces, cellular while
charging, unknown battery, unknown interface).

**Where the facts come from — the finding of the day.** The app runs under firejail, and
`/etc/sailjail/permissions/Internet.permission` grants an Internet-permitted app exactly
`com.jolla.lipstick.ConnectionSelector`, `org.ofono` and `com.jolla.PinQuery`. `net.connman`
and `com.nokia.mce` are **not** on the list, so `Nemo.Mce` and connman's signals are out no
matter how convenient they would be. The same sandbox may read the kernel the daemons read
(its profile adds only `--private-bin`, no private `/sys` or `/proc`), so
`src/kelpdevicestate.{h,cpp}` reads `/sys/class/power_supply/*` for the battery and
`QNetworkInterface` plus `/sys/class/net` for the connection, polling every 20 s and at
startup, and logging the verdict whenever it changes because the cellular names are a
heuristic. `src/kelppolicy.{h,cpp}` combines the switches, the device state and the rule
into `mayServe` / `block` (`""`, `"metered"`, `"battery"`) plus `lowBatteryPercent` for the
wording; QML is given the reason as a *token*, never as a sentence.

**The orchestration reuses the existing verbs, which is the point.** The root QML reacts
to a block by pausing each affected share with the existing `pause()` — so the stop is
non-destructive, the row keeps its link, and the stop is **not** written to `shares.json`
as a user pause (a restart comes back serving, and a pause the user did ask for is never
overwritten). `policyStopped` accumulates ids (so a share added while blocked cannot evict
an earlier one), and `addBundle`/`resumeShare` re-apply the policy, so a share created or
resumed *while* blocked is stopped at once rather than slipping out. Unblocking republishes
the remembered ids. Nothing new closes the listener, so the ephemeral port does not move.

**Verified on the emulator, with force inputs.** Two environment variables make the
unreachable reachable there (`KELP_FORCE_METERED=1`, `KELP_FORCE_BATTERY=<0..100>`, read
once at startup, deliberately outside the dev-extras bundle because they can only make the
app *more* conservative). The app's own log is the evidence, quoted with no link text in it:

```
KelpPolicy: serving stopped - "on forced0 (cellular), battery 98% discharging" - Wi-Fi only on
KelpPolicy: 2 share(s) stopped — metered
KeepAlive: background serving off (setting on, 0 served, 0 previewing)
  /info right token -> 401 bad token          <- run-emu-share.sh --fetch
  result: NOT SERVING
KVERIFY flip off: wifiOnly true -> false
KelpPolicy: serving allowed again - "on forced0 (cellular), battery 98% discharging"
KelpPolicy: serving "kelp-demo" again
KelpPolicy: serving "web" again
```

and the battery branch, forced to 5% discharging: `KelpPolicy: serving stopped - "on eth0
(other), battery 5% discharging"`, `KelpPolicy: 2 share(s) stopped — battery`, `KeepAlive:
… off`, probe `401` / `NOT SERVING`. While blocked the listener still answers `401` rather
than dropping the connection, exactly as a paused share does.

**The claim that changed, and why it is a better one.** This batch's plan said a resumed
share would mint **byte-identical** link text. Verification refuted it: `q=` is sealed
under a fresh random nonce every time, so the *text* always differs in that one blob. What
is true, and is what a recipient can feel, is that the link still *resolves* to the same
thing — same bundle id, same 43-byte bearer token, same host:port — because stopping a
share does not close the listener (there was no second `KelpServer: serving on` line across
the stop/resume). So the test is a fetch, not a hash: after the resume, inside the same
process, the probe fetched successfully through **both links that were minted before the
stop** (`--link 3` and `--link 4`, the oldest in the log), which is the whole reason for
choosing pause over stop. Two more things the log corrected: the emulator *does* have a
battery (98%, discharging — an assumption the plan had wrong), and the emulator's only
interface `eth0` classifies as `(other)`, i.e. unmetered, exactly as designed.

**Hygiene, done in passing.** Verifying printed two emulator links in the clear, so those
keys are spent: the two shares were re-sealed under fresh keys (new bundle ids, new
secrets, fresh objects), the old rows stopped and removed, and the 12 superseded objects
pruned (`cleaned up 12 unused object(s), 63183 bytes`) so the leaked keys have nothing left

### 3.29 K4: passphrase links (§12.3, verified live)

**What was parked.** A `kelp://` link *is* the capability: the fragment holds the key, so
forwarding a link forwards the bundle and there is no recall. Some hand-overs make that
awkward — a link pasted into a group chat, a link written on a whiteboard, a link mailed
through a mailbox nobody trusts. K4 adds a link whose key is *wrapped* under a passphrase:
the link alone opens nothing, and the passphrase travels separately.

**The form, and what it costs.** `#k=<secret>` becomes `#p=<blob>`, where the blob is

```
version(1) ‖ iterations(4, big-endian) ‖ salt(16) ‖ nonce(12) ‖ AES-256-GCM ct+tag(48)
```

81 bytes, 108 base64url characters. The plaintext is the same 32-byte master secret the
ordinary link carries, the key is `PBKDF2-HMAC-SHA256(NFC(passphrase), salt, iterations,
32)` — the user's choice over Argon2id, and it adds no dependency because libcrypto already
has it — and the **bundle id is the associated data**, so a blob cannot be lifted onto
another bundle's link. Everything else follows from the master secret, so sealing,
`q=`, the swarm token, the fetch, the preview and the row are untouched: the *only* new
thing in the app is that the secret has to be unwrapped before any of it works.

The iteration count travels *in the link*, which is what lets the default rise later
without breaking links already handed out; this build mints **600 000** and refuses to
derive more than **10 000 000**, because a link is untrusted input and the derivation is
deliberately slow. The passphrase is **never stored** — the row keeps the *wrapped blob*
(`passBlob`) beside the secret it already kept, which is what lets a restart mint the same
link again; losing the passphrase loses the link. A floor of 8 characters is enforced in
`KelpBundles::seal`, before anything is sealed, and hinted in the UI.

**`libkelp` half (pure, no I/O).** `Crypto::pbkdf2Sha256` (OpenSSL `PKCS5_PBKDF2_HMAC`,
pinned against RFC 7914 vectors produced with `openssl kdf` on the host) and the link
form itself: `WrappedVersion`/`WrappedHeaderSize`/`WrappedSize`/`SaltSize`/
`DefaultIterations`/`MaxIterations`, `wrapSecret`, `unlock`, `needsPassphrase`,
`wrappedParameters` (a permissive header read, safe on untrusted input — `unlock` is what
enforces the cap), and a `decode` that takes either fragment, refuses both at once, and
stashes `q=` for `unlock` to open. `encode` **fails closed** for a passphrase link: no
plaintext fallback, so a protected share cannot become an ordinary one by accident.
`tst_kelp` went **420 → 497**.

**App half.** `KelpBundles::seal(paths, name, page, passphrase)` wraps before publishing
(publishing is what mints the link, and the link has to know to carry `#p=`) and returns
the blob as `passBlob`; `publish`/`republish` carry the wrapped secret, and `republish`
refuses a stored blob it cannot read rather than publishing an ordinary link — **failing
open would hand out the key**. `linkInfo` gained `needsPassphrase`, and `unlockLink(link,
passphrase)` is new. `KelpClient::fetch`/`fetchForViewing` take the passphrase and unlock
in `beginFetch`, *before a source is created*, so a wrong passphrase costs the derivation
and never a network round trip. In QML: `AddPage` gained a *Protect the link* section above
the share buttons (one switch, one masked field, the share buttons disabled while it is too
short) and the passphrase is cleared from the field once the share is sealed; `OpenLinkPage`
shows a masked field and *Unlock* **instead of** the name/address/kind — there is nothing to
show, all of it is sealed — and holds the unlocked reading in the one object its existing
bindings read, so the page after unlocking is the page it always was; and the row carries
`passBlob` through `saveShares`, `restoreShares`, `resumeShare` and the policy resume.
(That page was *described* from its source here, but not instantiated: the live run below
drove `seal`/`linkInfo`/`unlockLink`/`fetch` from a hook, so a handler in the page that
could not exist went unseen then — see §3.30.)

**Off-device, first.** Both suites green in both build modes: `libkelp` **497** (was 420),
`tst_kelpbundles` **211** (159: a passphrase share's link says nothing — not the address, not

### 3.35 C4b, first slice: the gateway a browser with no app can open

**What it is.** Design §5.2's other half. The preview (§5.1) serves a page to a browser on a
device that has the app; the gateway serves one to a browser with nothing on it. Both live in
`C4b-plan.md`, which was written out completely before any code, per the standing rule.

**The decision that made it small.** A browser cannot present a token a publisher registered, so
the obvious gateway would add a token-less `/b/<id>/o/<objectId>` path — which would make every
published bundle's ciphertext enumerable by object id, exactly what C3's token path refuses. The
loader instead derives `relay_token` itself: the secret is in the fragment, WebCrypto has HKDF, so
the browser computes `HKDF-SHA256(secret, salt=∅, info="kelp/v1/relay")` and fetches through the
**existing** token-gated paths. The gateway therefore adds no data path at all — only a page and
its two scripts — and the relay still sees ciphertext only, from a client it cannot tell apart
from the app except by ALPN.

**What was built.** `KelpTls::setAlpnProtocols()` (the server accepts a list; the client still
offers, and still requires, `kelp/1` — the relay lists `kelp/1` and `http/1.1`), the `/b/` path
space in the relay (`/b/<id>` → 301 → `/b/<id>/` → the loader, `/b/<id>/.kelp/{core,page,sw}.js`),
and the loader itself as four files compiled into the relay with a `.qrc`: a bootstrap page, a
service worker that answers in the bundle's own URL space (§5.3) with the decrypted object and the
MIME the manifest records, and `core.js`, which holds the CBOR reader, the two derivations, the
object envelope, the tree walk and the §5.3 page rule — the mirror of libkelp's `Web`.

**Two things the tests caught, both real.** The 301's `Location` and the worker's
`Service-Worker-Allowed` were sent without their trailing slash, which would have put the page's
relative URLs — and the worker's scope — one level above the bundle's prefix. And a recipient that
disconnects while a WANT is in flight left a dangling `Pending` entry, so the publisher's answer
would have been written to a freed connection: rare for the app, routine for a browser, which
abandons requests constantly. `retire()` now drops the pending entries of the connection it is
retiring, and `tryRequest()` loops, so one kept-alive connection serves several requests (HTTP/1.0
clients, and anything that asks for `Connection: close`, are closed after the answer instead of
being left waiting).

**Evidence.**
- `relay/test/run-relay-test.sh`: 6 harness cases unchanged, plus **11 browser-shaped cases**
  driven by `openssl s_client -alpn http/1.1` against the same port while the harness holds its
  tunnel open — the redirect, the loader, both scripts, the worker's scope header, a malformed
  bundle id (404), a bundle's own file (404, the relay never serves it), `/info` and an object
  **over http/1.1 with the derived token**, a wrong token (401), the relay's own account of
  `ALPN "http/1.1"`, and two requests on one kept-alive connection. `ALL PASS`.
- `relay/gateway/test/run-gateway-test.sh` (host-side, needs `node`): `makefixture` seals three
  bundles with libkelp — a page at the root, a page in a subfolder, no page at all, plus a
  265 000-byte file that spans two chunks — and records libkelp's *own* answers (`Web::page`,
  `Web::mimeType`, the relay token). `core.test.cjs` then walks them in JavaScript: **61 checks,
  0 failures** — the token matches byte for byte, the entry/root/candidates match libkelp's rule,
  every MIME type matches the table, every file decrypts to the plaintext libkelp sealed
  (including the multi-chunk one), a substituted object is refused *before* decryption, a foreign
  key opens nothing, and the URL space resolves directories to `index.html` exactly as intended.
- Every existing suite still passes: libkelp 497, kelpfetch 37, kelpsettings 39, kelpshares 24,
  kelpqr 9, kelpbundles 219, kelppreview 206, kelpclient 152, relay `ALL PASS`.

**What is deliberately not built yet** (`C4b-plan.md` says each one out loud): passphrase links at
the gateway (`#p=` gets a plain "open it with the Kelp app"), a ZIP for a non-page bundle (the
file list downloads one file at a time), the app's *Copy browser link* button (the emulator test
can build the URL by hand), and — the one that matters operationally — **a deployment**: a browser
only gives a page WebCrypto and a service worker on a secure context, so a self-signed click-through
is not enough and a real certificate (or a CA the browser trusts in the test device) is a
prerequisite, not a detail.

### 3.36 C4b in a real browser: two bugs the unit tests were blind to

The relay's own browser-shaped cases (`openssl s_client -alpn http/1.1`) prove the *server* half,
and the 61 core checks prove the JavaScript against libkelp — but both drive `core.js` directly.
The seam between them — what the bootstrap hands the worker, and what the worker then asks the
relay for — was covered by two literals that agreed with each other and with nothing else. It took
a real browser to find it.

**The test.** In the emulator: the relay built for i486 and a CA the guest trusts (SAN
`IP:127.0.0.1`), the app sharing a three-file page (`index.html`, `style.css`, `sub/dot.txt`) with
its relay set to `127.0.0.1:9443`, and `sailfish-browser` opening
`https://127.0.0.1:9443/b/<bundle-id>#k=<secret>`.

**Bug 1 — the relay token, encoded twice.** Every object the worker asked for came back **401**,
and the page said "This file could not be fetched: the relay answered 401 for an object". The
bootstrap posted `token: base64UrlEncode(keys.relayToken)` — *text* — while `apiBase()` encodes the
token itself, so the worker sent a base64url string as if it were an address: a second encoding.
The loader's own `/info` kept working, because that path goes through `apiBase()` directly, which is
why only worker-served objects failed.

**Bug 2 — a file served as its own manifest.** With the token fixed, the page was **blank white**
(and would have been blank for any page, however long). `page.js` named each file by `file.hash`,
which is the *file manifest's* address, not the content's; the worker fetched that one object and
handed the browser a 50-byte CBOR manifest as `text/html`. A multi-chunk file would have been
truncated by the same mistake.

**The fix, and the seam it closes.** The handover is now one function in `core.js` rather than two
agreeing literals: `pageSession()` builds the message (both keys as the bytes they are; every URL
named by its **chunks, in order**) and `sessionFetcher()` is the worker's side of it. `sw.js`
fetches every chunk and concatenates, so a file longer than one chunk arrives whole — the same
shape the file list already downloads. `core.test.cjs` pins it per fixture bundle: the token and key
cross as 32 bytes, the entry is named by its chunks and *not* by its manifest, every URL served
through `sessionFetcher` decrypts to the digest libkelp computed for that path, and a worker fetch
puts the token in the URL exactly once.

**Evidence.**
- The emulator browser, three times over: first the 401, then blank white, then the page —
  heading, the bundle's own stylesheet applied, the nested `sub/dot.txt` fetched through the worker
  (its `alt` text visible where an image could not be), and the page's own script executed
  ("Inline JS ran: 12").
- The app's tunnel, for that page: `"127.0.0.1:9443: 9 object(s) wanted, 9 served (1961 byte(s)),
  0 not held of "gateway-test""` — the whole bundle, manifests and chunks, out of ciphertext the
  app sealed and the browser asked for by name.
- A host-side replay of exactly what `page.js` and `sw.js` do, against the live relay over an
  `ssh -L` forward, printing what each URL resolves to: `"" → index.html 464 bytes`, `style.css
  98 bytes`, `sub/dot.txt 50 bytes` — the sealed plaintext, byte for byte. This is the check that
  found bug 2: with the old session shape the same replay printed 50-byte CBOR for all three.
- `core.test.cjs` **71 checks, 0 failures**; the relay harness `ALL PASS`; every app suite
  unchanged (libkelp 497, kelpfetch 37, kelpsettings 39, kelpshares 24, kelpqr 9, kelpbundles 219,
  kelppreview 206, kelpclient 152).
- Noted while testing: killing the relay does not need the app restarted — `KelpTunnel` retries and
  re-publishes by itself, so a link already handed out keeps working.

### 3.37 C4b slice 4: the app's *Copy browser link*

> **Withdrawn 2026-10-21.** The relay address field and this button were removed; the app
> shares and fetches on the LAN only. See §3.42. This section is the record of the build and
> its evidence.

The emulator test in §3.36 built `https://<relay>/b/<id>#k=<secret>` by hand. A sender cannot be
expected to: on a webpage share's page there is now **Copy browser link**, beside *Open in
browser*. The design was written out first (`C4b-plan.md`, "Slice 4"), because four of its choices
are security choices rather than layout ones.

**The four choices.**
- **The relay is the share's own** (`linkParts.relays[0]`), not the Settings field. `setRelays()`
  only stores the list — it does not move an existing tunnel — so a URL built from Settings would
  name a relay that never heard of the bundle.
- **`https://`, with the port always written** (`:9443` when the relay string omits it). The relay
  is TLS-only, and WebCrypto plus a service worker need a secure context; the tunnel parser's
  default port means nothing to a browser.
- **No browser link for a passphrase share.** The app serves with the plaintext secret, so minting
  `#k=` would hand out exactly what the passphrase withholds — and D4 already refuses `#p=` at the
  gateway. The button is disabled and the page says a browser cannot ask for a passphrase.
- **No relay, no address, and it says why** — a LAN listener serves objects, not a loader.

The URL is copied, never logged or shown: it carries the key. `KelpBundles::browserUrl()` does the
checks (32-byte id, 32-byte key, a usable `host:port`) and the port normalisation, so the rules are
unit-tested (14 checks) rather than living in QML.

**A device test that first looked like a security bug, and was not.** The first emulator run showed
the button *enabled* on `kelp-demo`, a passphrase share, and it copied a key-bearing URL:
`VERIFY passphrase: button=found enabled=true clipboard-unchanged=false`. The cause was in the
guest's stored row, not in the code: `shares.json` had `"passBlob": ""` for that share, so the app
restored it as a plain `#k=` share. That file had been edited by hand in an earlier session (a
`head -16` trim to drop a test row) — the one writer outside the app that can lose a field. Every
path that touches the blob (`restoreShares`' two branches, `saveShares`, `resumeShare`,
`resumeSharesFromPolicy`, `addBundle`) carries it; a fresh seal stores a non-empty one; and a
restart now logs `restored "kelp-demo" … "(protected by a passphrase)"` and mints exactly one
`#p=` link. The gap this exposed was *coverage*: `tst_kelpshares` never looked at `passBlob` (or
`page`), the two fields a restart acts on besides the key. It does now (26 checks), so a code-level
loss cannot return silently.

**A second bug, from the same run: a paused share's note.** Pausing drops the row's link on purpose,
so the note's first branch saw "no link" and said *"This share's link cannot be read"* — damage
language for a deliberate state. The paused branch now comes first and says *"Resume this share to
copy a browser link: nothing is being served while it is paused."*

**How the page was driven.** `button.clicked()` from a QML hook fails on Silica's Button
(`Error: Insufficient arguments`), so the click body is a named command,
`BundlePage.copyBrowserLink()`, which the button calls and the hook calls by name. The refusal
guard lives in the command, which is what makes "call it while disabled" a real test rather than a
test of the disabled flag.

**Evidence (emulator, i486; hook removed afterwards).** Five states, all from the real page:
- web page + relay + serving: `enabled=true`; the copied 123 bytes start `https://127.0.0.1:9443/b/`,
  their fragment **is** the share's own key (`copied.slice(hash) === link.slice(linkHash)`), and they
  name the bundle;
- passphrase share: `enabled=false`, the passphrase note, clipboard unchanged even when the command
  is called directly (the guard, not the disabled state, refuses);
- paused: `enabled=false`, "Resume this share…" (after the ordering fix);
- no relay: `enabled=false`, "A browser link needs a relay…";
- **after a restart**: the passphrase share still restores as protected and its button is still
  disabled — the state the first run got wrong.

Suites: libkelp 497, kelpfetch 37, kelpsettings 39, kelpshares 26, kelpqr 9, kelpbundles 233,
kelppreview 206, kelpclient 152 — all 0 failures; QML smoke 9/9 Ready.

**Not built, still:** `#p=` at the gateway, and the browser-trusted certificate that makes any of
this usable beyond a test rig (item (c) of next-step 22).

### 3.38 "Another transfer is still running" now names the transfer

**Symptom, raised by the user.** §3.32 stopped a *foreign* transfer from offering a spinner
and a Cancel, which was right — but what is left says nothing: *Another transfer is still
running…*, with no word about which one. And that row can appear on a link the person never
pressed anything for: a link handed over by another app (scheme activation, §3.37) is
prefilled while an earlier transfer is still in flight, so someone looking at their own link
is told to wait for something they cannot see, name or stop.

**Design.** The client holds the one fact worth showing — `kelpClient.name`, the sanitised
name of the fetch in progress, set beside the link it is handling in `beginFetch()` — so the
row names it:

- the sentence keeps §3.32's words and gains the name: *Another transfer is still running:
  “kelp-demo”*;
- **no name, no invention.** A link that carried no `n=` keeps the old sentence exactly as it
  was; a bundle id (or an id prefix) would be an identifying string to a person who has
  nothing to match it against. The name is only shown because the sender chose it;
- **nothing else about the row changes**: still no spinner and still no Cancel for a transfer
  this page does not own (§3.32) — those would act on someone else's work;
- the sentence moves out of the label's inline binding into a page property **`busyText`**,
  which the label binds to. The row's wording is then one named thing, the way
  `downloadLabel` already is, and a test can read the exact string the row shows instead of
  re-deriving it;
- **deliberately not done:** no special wording for a foreign *view* (a page being fetched for
  the browser) and no "go to that page" affordance. Cancel belongs to the page that started the
  transfer, and that page is where its progress is; this row stays a sentence.

**What could go wrong, and why it does not.** `name` belongs to the transfer in flight, not to
this page's link: `reset()` clears it and `beginFetch()` sets it in the same breath as
`m_link`, and the row is only drawn while `busy` is true — so a stale name cannot be shown for
a finished transfer, and a foreign row always names the transfer that is actually running.

### 3.43 The LAN address stops being a restart-only snapshot

**Why.** Removing the relay field made the LAN the only serving path, and the app still bound
the address it found when a share was minted. A phone moving from one Wi-Fi network to another
(or losing the network and getting it back) kept a listener on the old address and kept showing
links with `l=` naming it; the only fix was to restart Kelp. A fresh link at restart was already
covered (§3.7), but the address could go stale *inside* one session.

**What changed.**
- `src/kelpserver.{h,cpp}`: a five-second address watcher. It re-reads the usable LAN address;
  if the listener is on a different one it closes and rebinds (the shared-bundle table is kept),
  if the address disappears it closes, and if one returns it rebinds. It emits `addressChanged`
  only when the address links advertise actually moves, including to empty. A closed listener
  drops half-read requests rather than leaving sockets on the old address. A bundle is registered
  before the bind is attempted, so a launch that starts with no address still has a share for the
  watcher to serve when one arrives. No TLS or relay path is involved; the socket is still bound
  to the LAN interface, never `0.0.0.0`.
- `src/kelpbundles.{h,cpp}`: `lanAddress` (for QML to know whether a link can be minted) and the
  `lanAddressChanged` forwarding signal.
- `qml/harbour-kelp.qml`: on that signal, republish each row that is still intended to serve
  (`seeding` or `offline`) in place. Paused and policy-stopped rows keep their empty links and
  are refreshed by their existing resume paths. This does **not** call `restoreShares()`: that
  appends rows, and these rows are already on screen. If the address is empty, the rows go
  `offline` and their links are cleared instead of being republished against a dead address.
- The honest limit: a link already sent to someone cannot be edited. The row shows a new link;
  the old one stays dead, like any copied link after a port or address change.

### 3.44 The preview can ask for the object it is missing (K3, the seam)

**Why.** `knobs-plan.md` K3 was deferred on 2026-10-18 because no app path could open a preview
session over an incomplete store: the owner's preview reads objects that storage management keeps
for its share row, and a view-only page is opened only after `KelpClient` fetched and verified the
whole bundle. The server's answer to a missing object was therefore `503`, and a source-backed
session would have had tests but no caller. This change supplies the caller — the view-only page
session — without turning the normal view into a lazy-open. A hole can now heal instead of ending
the page, and the seam a later lazy-open needs exists.

**What changed.**
- `src/kelppreviewserver.{h,cpp}`: a session may carry a `KelpSource`. A request that needs an
  object the store lacks is parked, not answered. The server asks its source for exactly the
  missing ids; duplicates join one fetch, and at most four objects are in flight, so a page with
  forty chunks open does not open forty sockets. The request waits until every object its answer
  needs is present, then writes the response. Each arriving object is checked against its id
  with `Kelp::storeReceived` before it is stored. A source failure or a 20-second deadline is
  `503`; bytes that do not match the id are `502`, because retrying the same address would only
  repeat the lie. A missing *manifest* is still `503`: path resolution names the data objects, so
  there is no id to ask for. Closing or sweeping a session answers its parked requests `404`.
  The session keeps `onDemand`/`mismatched` tallies. The failure log is deliberately generic; it
  does not repeat the source's own words, which for a relay can include an address.
- `src/kelpclient.{h,cpp}`: `openPageView()` hands the source it fetched with to the preview
  server and clears its own pointer; the session owns it from then on. The decoded link is kept
  (not logged) so a session re-minted after the idle sweep can get a fresh source — a passphrase
  link is not asked for its passphrase again. The owner's own preview passes no source. A
  test-only `forgetViewObject()` removes one id from the view's memory store, which is what makes
  the otherwise unreachable caller path testable.
- `src/tests/tst_kelppreview.{cpp,pro}` and `src/tests/tst_kelpclient.cpp`: the new fetch seam is
  exercised over a real socket, and the client test runs the whole path through a real
  `LanSource`.

### 3.45 Lazy-open: a received page paints before its content is all here

**Why.** §5.1's last open item, chosen by the user after K3. A view-only page link used to fetch and
verify the whole bundle before the session could open, so the browser waited for every asset even
though it would ask for only some of them. K3 had already built the server side of the answer: a
request for a missing data object is parked, fetched through a `KelpSource`, verified and served.
This change supplies the production caller and keeps the 32 MiB ceiling honest.

**The split.** Manifests (the root, directory manifests and file manifests) are small and are what
`Web::page`, `Web::resolve` and the server need to answer any path; they are all fetched first. Data
chunks are fetched only when the browser asks for an object that needs them. There is no background
fill. `Done` now means the manifest index is here, which is exactly when the QML already calls
`openPageView()`.

**What changed.**
- `libkelp/kelp_bundle.{h,cpp}`: new pure `missingManifests()`. The existing `Missing` walker gained
  one `manifestsOnly` flag: `visitFile()` still reads and decodes the file manifest (so a corrupt
  one is an error, not a hole), but does not name its chunks. `missingObjects()` is unchanged.
- `libkelp/kelp_store.h`: `ObjectStore::byteCount()` (default `-1` when a store cannot say cheaply),
  with `MemoryStore` overriding it. The on-disk app store is only used by unlimited owner previews.
- `src/kelpclient.{h,cpp}`: a view's walk uses `missingManifests()`; when it is empty, `finishViewing()`
  sets `Done` and logs that the index is here and content is on demand. `viewBytes()` reports the
  memory store's actual size, including objects the session fetches later. `openPageView()` passes
  the view ceiling to the server; a page-less bundle releases its source too. The test-only
  `forgetViewObject()` is gone.
- `src/kelppreviewserver.{h,cpp}`: `open()`/`openEntry()` take an optional absolute `storeLimit`
  (0 = unlimited). Before an on-demand object is stored, the session checks the store's current
  bytes plus the arriving object. If that would pass the limit it stops the session's fetches,
  answers every parked request `503` with a short "too large" body, records `Tally::overLimit`,
  and stores nothing. The source is stopped; no later object can fit either.
- `qml/pages/OpenLinkPage.qml`: a webpage view's busy line says "Preparing the page…" instead of
  "Fetched X of Y objects", which would now describe the manifest walk, not the page.

**Root-absolute page paths (2026-10-22).** The first live lazy-open browser pass on the emulator
showed the page HTML without its stylesheet, and links to subpages did the same. The page writes
its assets from the site root (`/wp-content/...`, `/category/...`), so the browser asked for them
at `http://127.0.0.1:<port>/...` rather than under `/<token>/...`; the preview correctly answered
404, because a root path has no token. The token is now also carried in a host-only loopback
cookie: every served file answers with `Set-Cookie: kelp_preview=<token>; Path=/; HttpOnly;
SameSite=Strict`, and `handle()` accepts that cookie for a request outside the token path. A
64-character hex first segment is still always read as a token, so an unknown token remains the
same 404. The cookie is never written to a log; it is the same read capability as the URL, scoped
to loopback and to the browser session. This keeps arbitrary root-absolute assets, CSS `url()`
references, JavaScript fetches and subpage links working without rewriting the page.

### 4.5 Reach the emulator's share from the LAN

The emulator cannot be dialled into (§6), so a link it mints names `10.0.2.15` and is
useless to any other device. Since §3.11 the app seals the address it advertises, so
only the app can name the host in a link: launch it with that address and link logging
on, then bridge the port.

**Which address, though.** This host has two real LANs: `10.42.0.228` on `enp0s25`
(the default route) and `172.28.172.3` on `wlp3s0`, which is the **phone's own
hotspot** — the phone is `172.28.172.1` and can only reach the second. A link that
names the default-route address is correct for the internet and dead for the phone, and
the app cannot know which one the recipient is on. Printing the other addresses was not
enough — the wrong one came back the next time the helper was run without an argument —
so the helper now **defaults to the Wi-Fi LAN** (`/sys/class/net/*/wireless`) instead of
the default route, and says so: a phone recipient is nearly always on Wi-Fi, often its
own hotspot, while a machine's default route usually leaves by wire. It lists the rest
and `--host` still overrides; a host whose default route *is* its Wi-Fi is unaffected.
Here that means `--relaunch` alone now serves on `172.28.172.3`: `2026-10-20 17:18`, the
helper advertising `172.28.172.3` and restarting the guest app, `serving on
"172.28.172.3:41409"`, the probe fetching the restored share through the forward (`/info`
200 with the token, 401 with none and with a wrong one, `result: serves`), the
publisher's tally line for that traffic, and the phone's own `curl` answering
`401 in 0.005 s` — reachable, and refusing as it should be (§3.30's verification had to
pass `--host 172.28.172.3` by hand; that is no longer needed).

On the host:

```sh

src/tests/run-emu-share.sh --host 172.28.172.3 --redact         # fragment removed
src/tests/run-emu-share.sh --host 172.28.172.3 --redact --fetch # also fetch it
```

**`--relaunch` does both halves of that for you** (2026-10-17, after the user hit this
twice: a share made after a *launcher* start names `10.0.2.15` and no phone can reach
it). It stops whatever app is running in the guest, starts it again with
`KELP_ADVERTISE_HOST=$HOST` and `KELP_DEBUG_LINK=1`, kills any forward left over from a
previous run — its port died with the restart, so it can only hold a listening socket
nobody will use — waits for the fresh `KelpServer: serving on` line, and only then opens
the new forward. It reads the log **from the point of the restart onwards**, so an earlier
run's `serving on` line (a dead port) can never be mistaken for the current one, and if
the app comes up serving nothing it says so and exits with the fresh, redacted log tail.
Verified in the same pass: `--relaunch --redact --qr` stopped the app, brought it up on a
new port (`serving on "172.28.172.3:44947"`), replaced the stale forward with one on that
port, printed the redacted link and wrote the QR — and a following `--fetch` answered
`200/200/401/401`, `result: serves`.

The script reads the app's own links out of the guest log, opens an ssh forward from this
host's LAN address into the guest, and prints them; if the app is advertising some other
address it says so and stops rather than print a link that cannot work. The guest port is
ephemeral, so re-run the script after the app restarts; it reuses an existing forward
when the port has not changed. `--qr` writes PNGs holding the key: treat them exactly like
the link itself, and do not leave them lying around.

`--fetch` goes on to fetch from the share through the forward, the way a recipient would —
an authenticated `/info` and root object, then two requests that must be refused — and prints
the publisher's own log line for that traffic (`kelp-probe.py`, §3.14). Nothing it prints
contains the key, so it is the quick answer to *is this share really reachable?* before a link
goes to a phone.

**Through the forward, the guest sees every peer as itself.** The port forward is dialled by
sshd *inside* the guest, so the connection arrives from `10.0.2.15` whether it came from this
host or from the phone. A traffic line (§3.14) made over the bridge therefore always names
`10.0.2.15`; that is the bridge, not Kelp.

Verified 2026-10-16 with the sealed link: an authenticated `/info`, sent from the guest
through the forward, answered `200 {"v":1,"objects":22,"files":6,"bytes":1687667}` and the
same request without a token answered `401`.

Re-verified 2026-10-16 after a restart (share *Screenshots*, 125 objects): the app logged
`bound to "10.0.2.15:43935"` / `serving on "172.28.172.3:43935"`, the script opened

answered `401` (the listener is really behind the forward), and the regenerated QR PNG
decoded to exactly the link the app had minted — same pre-`#k=` text, `q=` present. The
QR was checked with `src/tests/run-emu-share.sh --redact --qr`, so the key never left
the file and the log line above it. The previous run's forward (port 45525) and its QR
were stale — the port changes with every restart.

**The host must be on a network the phone can reach.** The emulator is only
reachable *through* this host, so the phone has to reach the **host's** address —
if it cannot, the fetch just times out with "could not reach the sender — no
answer" (§2.5) and looks like an app bug. On this machine the wired LAN
(`10.42.0.0/24`) is empty apart from its router, so a phone on Wi-Fi cannot see
the host at all (a full `/24` sweep found nothing). The host's Wi-Fi was

```sh

nmcli connection up "ei hyvää päivää"   # host becomes 172.28.172.3, same as the phone
```

Enabling Wi-Fi dropped the wired connection here. With more than one network up,

`--host <wifi-address>` whenever that is not the network the phone is on.
Verified 2026-10-16: with the host on `172.28.172.3`, the phone scanned the

### 4.8 The gateway in a browser with no relay and no certificate (§3.39)

The gateway page needs two things from its origin: a **secure context** (WebCrypto) and
same-origin `/v1/relay/…` fetches. Loopback gives the first for free, so a static tree on the
host's `127.0.0.1`, forwarded to the guest's `127.0.0.1`, is a real browser run without TLS, a
CA, or a running relay. The fixture the gateway suite builds has the real sealed bytes and the
real link:

```sh
cd /home/theb/Jolla/harbour-kelp
```

The page URL is the bundle's own link moved into the fragment —
`http://127.0.0.1:8080/b/<id>/#q=…&k=…`, exactly the shape `browserUrl()` mints. Build it in a
script from `fixture.json` and write it to a file; **never echo it** (it carries the fixture's
key, and the habit is the rule that matters).

```sh
python3 serve.py site 8080 &                 # any static server; /report?text=… writes a log
ssh -N -R 127.0.0.1:8080:127.0.0.1:8080 -p 2223 \
    -i ~/SailfishOS/vmshare/ssh/private_keys/sdk defaultuser@127.0.0.1 &
```

`http://127.0.0.1:8080` as an ordinary secure origin. Launch it with
`setsid sailfish-browser "$(cat /tmp/kelp-url.txt)&mode=zip"` over ssh; append `&mode=cancel` or
`&mode=cap` for the other two runs (the hook reads `mode` from the fragment and the page ignores
it).

The hook is the only test code: appended to the **served copy** of `page.js`, it waits for
`.allbar button`, reports its label/disabled state and the `.note`, clicks (or clicks Cancel a
second time), and reports the status line to `/report`. Nothing is installed on the guest, and
nothing is committed.

**Downloads are where the emulator stops.** Its embedlite `HelperAppDialog` reports
`browser.download.dir isn't enabled, will use prefferedDir` and waits for a save destination;
no file is written, for the ZIP **or** for the older per-file button (`Saved big.bin`, nothing
on disk). To get bytes, run a throwaway Firefox on the host against the same origin — loopback
there is also a secure context:

```sh

        "$(cat /tmp/kelp-url.txt)&mode=zip"
```

with `profile/user.js` holding `browser.download.userGestureTokenRequired=false`,
`browser.download.folderList=2`, `browser.download.dir=/tmp/kelp-live/downloads`,
`browser.download.useDownloadDir=true`. Then `unzip -t downloads/*.zip`, `unzip -Z1`, and compare
each file's sha256 with libkelp's own recorded digest. Remove the whole tree afterwards: it holds
the fixture's key.

**On the phone the write does happen, and no CA is needed.** The C2's browser hands the same
blob to `nemo-transferengine`, which writes it to `~/Downloads` — per-file and ZIP alike

```sh

```

Open the URL with the running browser's D-Bus method:

```sh

    array:string:"$URL"
```

visible. Keep the URL in a file on the phone (it carries the key), and delete the tree and the
downloads afterwards.

**If you instead want the emulator's browser to trust a real TLS origin**, its profile is at
`~/.local/share/org.sailfishos/browser/.mozilla/`; it is NSS, not the system store. The system
CA path (`/etc/pki/ca-trust/source/anchors` + `update-ca-trust`) is not what Gecko reads there,
and this host has no `certutil`, which is why the loopback route above is the recipe.

## 5. Driving a transfer

Two shapes, both used:

**(a) Two devices** — what was used today. On the sender: pick the entry, *Start
sharing*, then take the link (`Copy link` in the UI, or the log with
`KELP_DEBUG_LINK=1`). On the receiver: launch with `KELP_INITIAL_LINK=<link>` (or
paste it into *Open a link*) and tap *Download*.

**(b) One machine, two instances** — the original scheme, still valid: run the
sender and the receiver with different `XDG_DATA_HOME` so they have separate
stores and logs, and they will fetch over the real LAN address of the machine.

Verify a transfer with numbers, not impressions:

```sh
# receiver store: one file per object, sharded ab/<64-hex>
find ~/.local/share/harbour.kelp/harbour-kelp/objects -type f | wc -l
# the log says what it did
grep -E "round|objects are here|wrote" ~/.local/share/harbour.kelp/harbour-kelp/kelp.log
# and the content itself
sha256sum ~/Downloads/<name>
```

For a whole tree, `diff -r` the written folder against the original and compare
`sha256sum` of the two sides — that is how C2b and C3 were signed off.

## 6. Traps (each of these cost time)

- **`grep`/`pkill -f` match their own command line.** On the device,
  `ps aux | grep harbour-kelp` inside an `ssh '…'` call matches the ssh command
  itself and reports a phantom process. Ask the kernel instead:
  `for p in /proc/[0-9]*; do [ "$(cat $p/comm)" = harbour-kelp ] && echo ${p#/proc/}; done`
  and never `pkill -f /usr/bin/harbour-kelp` — it can kill your own session.
- **`pkill -x harbour-kelp` does not stop the app on the emulator.** Observed
  2026-10-16: after several launches, nine `harbour-kelp` processes were still
  running (state `S`), and `pkill -x` left them untouched — so a "fresh" run was
  actually two instances writing to the same log, which is very confusing to
  read. Kill by pid from the loop above: `... && kill -9 "${p#/proc/}"; done`.
  After the kill, re-check the count is zero before trusting a run.
- **Unload KVM before starting the emulator.** On this Linux host
  `sfdk emulator start` fails into a start-stop loop with
  `VERR_VMX_IN_VMX_ROOT_MODE` while `kvm_intel` is loaded. Ask the user to run
  `sudo modprobe -r kvm_intel kvm` first (it needs sudo; the agent does not have
  it). This is in the sailfish-os-dev skill (`environment-setup.md`) — read it
  before touching the emulator.
- **The emulator cannot be reached inbound.** It sits behind QEMU user NAT
  (guest `10.0.2.15`); the host cannot open a connection to a guest listener.
  Reach host-side services with `ssh -N -L 127.0.0.1:9999:<guest-ip>:<port>`, and
  kill such tunnels with
  `ps -eo pid,args | awk '/[s]sh/ && /9999/ {print $1}' | xargs kill`.
  The *guest* reaching a LAN host works fine. To share *from* the emulator,
  `src/tests/run-emu-share.sh` (§4.5) does the forwarding and reads the app's
  own sealed links.
- **The share's address is captured when it is shared.** The link carries the
  interface address chosen at that moment; if the device changes network within a
  session the link goes stale and the recipient gets "could not reach the
  sender" (§2.5). Nothing re-announces it mid-session; a restart re-mints the
  link from the persisted share (§3.7).
- **`KELP_ADVERTISE_HOST` lasts exactly one launch.** Any restart without it —
  including one a test helper does while putting the device back — quietly reverts
  the links to `10.0.2.15`, which is correct for the app and useless off the
  emulator. Observed 2026-10-16: after a storage-test restore relaunched the app
  plainly, a scan said *no address to fetch*. The bridge both advertises and
  forwards, so re-apply the launch line from §4.5 whenever the app is restarted,
  and re-run `run-emu-share.sh` (the port changes with every restart).
- **"No address to fetch from yet" is a *reader* that could not open the address
  block, not a link without one.** Since §3.11 the address is sealed into `q=`
  under the link's own fragment, so a build older than that finds no `l=` and
  reports no address — identical to the message for a link that genuinely carries
  none. A current build on a sealed link always shows *Fetching from <address>*
  (right or wrong) and only fails later with "could not reach the sender". Check
  the reader's build before hunting for a link-side bug.
- **A sealed `q=` block cannot be decoded on this host.** There is no
  `cryptography`/`Crypto` module here, so the address inside a sealed link is only
  readable by a Kelp build (the app, or `tst_kelpfetch`'s encode→decode→create
  path). Judge the address from the app's own `KelpServer: serving on "…"` line
  (§4.5), which is the value `publish()` seals.
- **The recipient must share a network with *this host*, not with the emulator.**
  The emulator is reachable only through the host (§4.5), so if the phone cannot
  reach the host's address the fetch times out as "could not reach the sender —
  no answer" and looks like an app bug. Here the wired LAN is empty/isolated and
  the host's Wi-Fi was software-disabled (`nmcli radio wifi on`, then join the
  phone's network). Two consequences worth remembering: enabling Wi-Fi dropped the
  wired link, and the script's default `--host` follows the default route, so name
  the address explicitly when several networks are up.
- **The emulator has no clipboard a shell can reach.** `wl-copy`/`xclip` are
  absent. `KELP_DEBUG_LINK` and `KELP_INITIAL_LINK` exist for this.
- **`open()` holds the whole tree in memory.** The save path no longer calls it:
  `KelpClient` streams one file and one chunk at a time (§3.46), so a 335.6 MiB
  folder saves on the 1 GB emulator with no swap. Code that still asks `open()`
  for a tree pays for its size; keep that in mind for future callers.
- **Never record a link's `#k=` fragment.** It is the decryption key; anyone
  holding it can read the bundle. Redact it in docs, logs and chat. (Clearing a
  link out of the log is housekeeping, not revocation: the same secret is the
  share's persisted identity in owner-only `shares.json`, by design — the log copy
  is only a convenience for a device with no clipboard.)
- **In-source generated files shadow out-of-source test builds.** The app
  builds in place, so `kelpfetch.moc`/`moc_*.cpp` sit at the tree root. A test
  `.pro` whose `INCLUDEPATH` leaks the project root can make the compiler pick
  up a *stale* root `kelpfetch.moc` instead of the fresh one — this produced
  duplicate moc symbols at link. The `src/tests` project deliberately omits
  `$$PWD/../..` from `INCLUDEPATH` (with a comment saying why); if a new test
  target hits duplicate `qt_static_metacall` symbols, check for a stale
  generated file shadowing first, and remember a target switch needs
  `rm -f harbour-kelp *.o moc_*.cpp Makefile .qmake.stash` (§4.1).
- **A define is invisible to `make`.** `KELP_DEV_EXTRAS` becomes `KELP_DEV_BUILD`
  (src/kelpbuild.pri) and changes real behaviour, and `make` does not notice a
  command-line change: flipping it — or the spec's `%define kelp_dev_extras` — on an
  incremental build leaves a stale `devExtras()` compiled in, so the build is
  quietly still the mode it was last compiled as, and no warning says so.
  `harbour-kelp.pro` now touches every file whose compilation depends on a define,
  but the habit is a clean (§4.1, §3.18).
- **A build can print the dev-extras switch twice — trust the second one's context.**
  `%qmake5_install` is a `make install`, so a stale Makefile (e.g. because a `.pro` was
  edited while the build ran) is regenerated by a qmake that has no `KELP_DEV_EXTRAS`:
  the spec exports it only in `%build`. Observed as `Kelp: dev extras ON` followed by
  `dev extras off — release build` in one aarch64 build; the second is a Makefile
  regeneration after compiling, not a recompile — but it means the mode of a build is
  decided by whichever Makefile compiled the objects, so read the Makefile
  (`grep KELP_DEV_BUILD Makefile`) or rebuild without touching inputs (§3.18).
- **The About page's build id is a UTC timestamp, not the commit.** `BUILD_ID` prefers
  `git rev-parse --short HEAD` and falls back to `date -u` (harbour-kelp.pro), and the SDK
  build engine has no `git` at all (`sh: git: command not found`), so every packaged build
  takes the fallback: `20261017-103244` is a time, not a revision. Identify a build by what
  it logs (`Kelp: build mode — dev extras on|off`, then `Kelp <version> (build …)`), not by
  that string. The host repo is fine — `git log` there is the history.
- **A test that talks to a listener in its own thread must run the event loop.**
  `KelpServer` is a `QTcpServer` in the same thread as the test, so its
  `newConnection` slot only runs when control returns to the event loop. A helper
  that blocks in `waitForConnected`/`waitForReadyRead` — the obvious way to write
  an HTTP GET — never gives the listener the chance to accept, so every request
  times out with an empty reply and the failure looks like a server bug. Drive
  the socket with signals and a `QEventLoop` instead (`tst_kelpbundles`,
  `httpGet`).
- **Sailfish's Qt is 5.6.** Not 5.15: `QAbstractSocket` has no `errorOccurred`
  (the signal is a plain, overloaded `error`), `QOverload` does not exist, and
  neither does anything else from 5.7+. Select an overloaded signal with an
  explicit `static_cast<void (QAbstractSocket::*)(QAbstractSocket::SocketError)>(
  &QAbstractSocket::error)` and check the header rather than the docs when a Qt
  API "should" exist.
- **A relay refuses a client that does not offer ALPN `kelp/1`.** `KelpTls` tears
  the connection down after a handshake that negotiated anything else, or nothing
  — that is what pins the protocol version (wire spec §1.2). So a relay's HTTP side
  cannot be probed with `curl` or `openssl s_client` the way the LAN listener can:
  the client has to offer the ALPN name first (python's `ssl` can,
  `set_alpn_protocols`). The tunnel also accepts **any** certificate
  (`SSL_VERIFY_NONE`, wire spec §224: peers accept any cert because every object is
  hash-verified), which is why the relay harness's self-signed certificate is
  enough for the app's own tunnel — no pinning to work around.
- **Silica's `DialogHeader` logs a `TypeError` while it is only declared.**
  Opening a page that declares a `Dialog` with a `DialogHeader` (the QR dialog on
  *Bundle*, the confirm dialog on *Settings → Storage*) warns
  `DialogHeader.qml:175: TypeError: Cannot read property 'backIndicatorDown' of
  null` — its `pageStack` is not resolvable yet, because the dialog is not open.
  It appears on a real page push, not only under a test hook, and the dialogs work
  (both verified live); it is Silica's own binding, printed once at page load, and
  nothing to chase.

- **QML warnings do not reach a redirected stderr file.** Qt routes them to
  journald, and the app's message handler mirrors every Qt message — QML
  TypeErrors included — into `kelp.log`. So `grep -aE "WARN |ERROR" kelp.log`
  since the last `---- log opened ----` is the real "did the page load clean"
  check; grepping the launch's stderr is not (§3.16, found by reading the
  sailfish-os-dev skill's `testing-debugging.md`).
- **Do not call `ListModel.get()` from inside a binding.** The cover's
  `servedCount()` did exactly that, and the moment a row changed in place
  (`setProperty`) while the cover was visible, QML reported `Binding loop
  detected` — `get()` re-enters the model while the binding itself is
  evaluating. Maintain the derived values as properties on the store
  (`servedShares`/`pausedShares`, refreshed wherever every row change funnels
  through) and bind to those. That is also why BundlePage re-reads its row on the
  store's `sharesRevision` counter rather than expecting the model to notify it.

- **The guest's `grep` is BusyBox: no `--line-buffered`.** A long-running
  `ssh 'tail -f log | grep …'` watcher dies instantly with "unrecognized option"
  on this image, and — for the same reason — even a working `grep` would hold its
  output in a 4 KB block buffer, so the file looks empty while the lines are
  really there. Use `awk '/pat/{print; fflush()}'` for a stream, and when in
  doubt read the log directly (§3.17, §3.16).

- **The guest has no `wget` applet and no browser.** Its busybox omits `wget`
  entirely, so to drive an HTTP endpoint on the device from the device (the only
  way — the emulator's loopback is unreachable from the host) use
  `/usr/bin/curl`, which *is* installed. And `sailfish-browser` is absent from
  the image: `Qt.openUrlExternally` still returns `true` and nothing opens, so
  the emulator cannot test a browser hand-off at all (§3.20).

- **A delegate's own property shadows a model role of the same name.** An
  unqualified `state` in a `ListItem` delegate reads `Item::state` (always `""`),
  never the model's `state` role — so the share list said "Offline" for every row
  and a paused share could not be resumed, while every non-delegate reader
  (`bundlesModel.get(i).state`) was correct. Give the role a name no `Item` has
  (`shareState`) and it works everywhere. The same class of mistake, one line
  over: a delegate binding to a role that a *row* lacks throws
  `ReferenceError: <role> is not defined`, so every `append()` must carry every
  key the delegate reads (§2.6, §3.21).

- **`grabToImage` renders the page without the ambience's wallpaper.** The
  screenshots the app takes are a white backdrop with the theme's *primary*
  colour (near-white on the dark ambience) drawn on it, so button labels and
  switch titles look washed out or invisible while secondary-coloured text reads
  normally. Take those images as evidence of layout and text content, not of
  colour (§3.21).

- **`pkill -f /usr/bin/harbour-kelp` over ssh kills the ssh command itself.**
  `-f` matches the whole command line, and the remote shell running the command
  has that string in *its* command line, so the shell dies with the app (ssh
  exits 255 and prints nothing). BusyBox's `pgrep -x`/`pkill -x` did not match
  the app either, so a "stopped" that was never checked left two app instances
  running against one log and one `shares.json`. Use `killall harbour-kelp`, then
  **check** with `ps -o pid,comm | grep harbour` that exactly one process is
  left (§3.21).

- **A QML change handler runs before a derived binding is re-evaluated** (found
  2026-10-18, §3.25, and the reason a fix can look right and do nothing). With
  `property bool viewOpen: …phase === "done" && kelpClient.isHandling(link)`, the
  probe inside `onPhaseChanged` printed the *previous* state — `phase=done
  viewOpen=false` on the way in, and `phase=idle viewOpen=true` on a later fetch,
  which fired a stray *Open in browser* on the old page. Two consequences worth
  remembering: an imperative path (a handler, or anything it calls) must read the
  primitives itself rather than a derived property, and a stale-derived-property
  read is silent — no warning, no error, just the wrong branch. The page keeps the
  binding for the UI and calls `viewIsOpenNow()` for decisions.

- **A QML hook cannot press a Silica `Button` with `button.clicked()`.** `clicked`
  is `MouseArea`'s signal, and `MouseArea`'s is `clicked(MouseEvent)`, so emitting
  it without the event logs `Error: Insufficient arguments` once a second and the
  handler never runs. Emit it with a null event — `button.clicked(null)` — which
  is what the app's own hook verification does; the page's handler does not read
  the event (§3.22).

- **`pruneStore()` empties object files but leaves the shard directories.** After a
  prune to 4 objects the store directory held 172 directories and 760 KB, 168 of
  them empty (4 KB each); the app's own `bytes` counts *objects* and says nothing
  about the filesystem, so Settings → Storage can honestly report a few kilobytes
  while the directory occupies most of a megabyte. Harmless, but the fix belongs in
  `KelpObjectStore`: drop a shard directory when its last object goes (§3.22,
  design §12.7).

- **The `web` demo share's secret was read out of `shares.json` by hand.** The
  file is `0600` and nothing in the app leaked it, but a secret that has been
  pasted anywhere is spent: re-share the folder to mint a new one before sending
  that link to anyone. Done for this session's demo share (§3.22, §9) — and note
  the side effect that makes it real: `unshare` + `seal` + `addBundle` is the
  whole rotation, and the old share's objects are then just unused objects for
  *Storage → Remove unused objects* to reclaim.

- **A QML item walker must skip children that are not `Item`s.** Walking a page
  with `for (i < root.children.length) … ktexts(c, …)` throws
  `TypeError: Cannot read property 'length' of undefined` the moment it reaches a
  `ListModel`, `Timer` or `Connections` — none of which has `children` — once per
  tick, forever. The C4a.2 walker got away with it by luck; guard the recursion
  (`if (!root || !root.children) return`) (§3.26).

- **Silica's `PageStack` drops a `push` made in the same tick as a `pop`.** The
  push returns, no error is logged, and `currentPage` is still the page that was
  *under* the popped one — so a hook that pops and pushes in one timer tick ends up
  inspecting the wrong page (it showed the bundle-list rows as "the page"). One
  state per tick fixes it. The same tick can be trusted for a page that was pushed
  in the *previous* tick (§3.26).

- **A sandboxed Sailfish app may not talk to connman or MCE, but may read the
  kernel.** `/etc/sailjail/permissions/Internet.permission` grants an
  Internet-permitted app exactly `com.jolla.lipstick.ConnectionSelector`,
  `org.ofono` and `com.jolla.PinQuery` — `net.connman` and `com.nokia.mce` are not
  on the list, so `QNetworkConfigurationManager` is empty, `Nemo.Mce` has no bus
  name to talk to and connman's signals never arrive, however natural the code
  looks. The app's firejail profile adds only `--private-bin`, with no private
  `/sys` or `/proc`, so the same app may read the interfaces the daemons read:
  `/sys/class/power_supply/*` (battery, with `status`/`capacity`) and
  `QNetworkInterface` plus `/sys/class/net/<if>/wireless`. That is where
  `KelpDeviceState` gets both inputs; the D-Bus routes are a dead end that looks
  alive (design §12.8, §3.28).

- **`qInfo() << (cond ? QStringLiteral("x") : QString())` logs a bare `""`.** A
  `QString()` in a `QDebug` stream prints as `""` (with the space before it), so a
  conditional segment makes every healthy line end in `""`. Compose the line into
  one `QString` and stream it once — `qInfo().noquote() << line`, because QDebug
  *quotes any QString with a space in it*, so without `noquote()` the whole line
  would come out wrapped in quotes (that is why `KelpServer`'s tally, which
  composes without it, reads `KelpServer: "10.0.2.15: …"`, §3.28). Introduced and
  fixed in K4: `sealed`/`restored` grew the conditional and every ordinary share's
  line ended in `""` until it was composed (§3.29). A line that carries
  **untrusted** text is the exception: `KelpClient: fetching` keeps the streamed
  form and its trailing `""`, because it is the only thing escaping an
  attacker-chosen bundle label and source address — a composed line would let a
  hostile link write a fake line into the receiver's log, `KelpBundles: link`
  included.

- **In QML the client's state is *properties*, not methods.** `kelpClient.error`,
  `.phase`, `.files`, `.bytes`, `.busy`, `.destination` are `Q_PROPERTY`s, so
  `kelpClient.error()` is a `TypeError` ("Property 'error' … is not a function")
  and the handler simply stops where it stands — which reads exactly like the app
  refusing to continue. `fetch()`, `cancel()`, `reset()`, `isHandling()`,
  `openPageView()` and `directory = …` *are* callables. A hook that gets this
  wrong will look like a product bug; check the QML context by grep before
  blaming the app (§3.29).

- **A hook cannot add a second `Component.onCompleted` to the root object.**
  Attach the work to a single-shot `Timer { interval: 2500; running: true }`
  instead: it runs after `Component.onCompleted`'s own work (relays, restores,
  policy) and needs no edit to the app's own lines.

- **Two LANs on the host: the default route is not the phone's network.** `enp0s25`
  is `10.42.0.228` (default route, internet) and `wlp3s0` is `172.28.172.3` — the
  phone's **own hotspot**, with the phone at `172.28.172.1`. A share link names one
  address (the app cannot know which side the recipient is on), so a link minted
  against the default route is unreachable from the phone even though the TCP forward
  is healthy. `src/tests/run-emu-share.sh` now prefers the Wi-Fi LAN and prints which
  address it picked, so `--relaunch` alone is right here; use `--host 172.28.172.3` when
  it has to be that one exactly. Verify reachability from the phone itself
  (`curl http://172.28.172.3:<port>/` answering `404`, or `/info` answering `401`)
  before blaming a link.

- **`Error: can't chdir to privileged` from a shell is the device, not the app — and the
  emulator can never show it.** Launching *any* Sailjail application from a shell on the C2
  prints, before the app's own output:

  ```
  Error: can't chdir to privileged
  constructing /run/firejail/mnt/privileged: Images ...
  mounting /run/firejail/mnt/privileged @ /home/defaultuser/.local/share/system/privileged
  hiding /run/firejail/mnt/privileged
  Warning: /usr/bin/bwrap was not disabled
  Error: can't chdir to privileged
  ```

  Firejail then **carries on**: `sailjail -p harbour-zendecoder.desktop
  /usr/bin/harbour-zendecoder` printed exactly that and the app still came up with
  `NoNewPrivs 1`, `Seccomp 2` (`/proc/<pid>/status`) — a real, applied sandbox. It is
  Sailfish's Firejail patch (the `privileged-data` rule in every `Base.permission`): the
  `privileged` user data is group-owned (`privileged`, `0770`) and its bind needs the setgid
  `sailjail` wrapper running with *real* gid `privileged`, since the sandbox is also
  `no-new-privs` (see the Sailjail docs). A launch that does not go through that wrapper —
  a shell, an emulator `gio open` — loses only that bind, not the sandbox. Lipstick's own
  launch of Kelp is unaffected because it *does* go through `sailjail`, which is why the
  running instance was always sandboxed properly. The SDK emulator's `firejail` is an older
  build (417 KB against the phone's 464 KB) without the `privileged-data` step, so the same
  command there is silent: **do not go "fixing" the app because the phone is noisier than
  the emulator.** Diagnosed 2026-10-20 by comparing the two devices with `sailjail -p`,
  `gio launch` and `/proc/<pid>/status`.

- **On the phone, `gio open kelp://…` hands the link over even when it looks like it did
  nothing.** It looks like a failure — the terminal prints the firejail noise above and no
  window appears — but the phone's own log says otherwise, twice in a row:

  ```
  17:43:57 INFO  Kelp: a link was handed over by another app
  17:43:57 INFO  Kelp: handed the link to the running instance
  17:47:46 INFO  Kelp: a link was handed over by another app
  17:47:46 INFO  Kelp: handed the link to the running instance
  ```

  The second line is the *forwarder's* own (it connected to `link.sock` and exited); the
  first is the running instance receiving it. What is missing is only the window coming
  forward, which a backgrounded Kelp cannot do on this platform (§3.23, `scheme-plan.md`).
  On the phone, check the log before concluding that activation failed.

- **A page is compiled only when it is pushed — and one bad property blanks it.**
  `pageStack.push(…)` on a document that assigns a property the type does not
  have shows **Could not load page** and logs a single `WARN` naming the file and
  line (`OpenLinkPage.qml:345:21: Cannot assign to non-existent property
  "onAccepted"`, §3.30). Sailfish's `TextField` (and `PasswordField`) have **no
  `accepted` signal**, unlike Qt Quick's `TextField`: the input method's
  `accepted()` is not re-emitted by `private/TextBase.qml`. Grep the Silica
  `qmltypes` before wiring a handler, and never trust "the app starts" as proof a
  lazily-pushed page loads. Compile the pages explicitly:
  `Qt.createComponent("pages/X.qml").status === Component.Ready` (1) from a
  hook catches this class in one second (§3.30). The page was shipped this way
  through K4 and only surfaced when a person tapped the menu item.

- **`bundlesModel.get()` goes blank after `remove()`.** A rotation loop that reads
  `row.name`/`row.path` (or passes the row to `addBundle`) *after* `bundlesModel.remove(i)`
  gets `undefined` for every role — the object is invalidated with the row. Copy what you need
  into a plain object first (§3.33). The blank rows then save as `""`, and the bundle still
  serves, so the breakage is easy to miss until a restart.

- **A ZIP's central directory must count itself.** Appending the central headers without
  advancing the write offset makes a well-formed-looking archive whose end record claims a
  0-byte directory; `unzip` then says *"N extra bytes at beginning… -N bytes too long"* and
  every entry still lists. The gateway writer had exactly this until `unzip -t` was put in the
  suite (§3.39). Build the archive in a test that a foreign tool reads, not only in the code
  that wrote it.

- **The emulator's browser reports a saved download that it never wrote.** Its embedlite
  `HelperAppDialog` logs `browser.download.dir isn't enabled, will use prefferedDir` and waits
  for a save destination, so no file appears — for the older per-file button too. The page's
  *Saved …* line only says the blob was handed over. Get bytes from a throwaway Firefox on the
  host against the same loopback origin (§4.8); do not read the absence of a file as an app bug.

- **A fixture that opens `q=` from a `kelp://` link hides the browser link's own shape.** The
  archive name test passed while `browserUrl()` still minted `#k=` only, so the real flow could
  never have received the label. Any feature whose inputs come from the *gateway URL* must be
  tested from that URL, not from the kelp:// link the app also holds (§3.39).

## 8. Decisions already taken — don't relitigate

Name **Kelp**, app id `harbour-kelp`, scheme `kelp://`. SHA-256
content-addressing with canonical CBOR manifests; AES-256-GCM; the key rides in
the URL fragment and never leaves it. Identity is hashed, location and key are
not: `bundle_id = SHA-256` of the root manifest, location and key in the query and
fragment (`r=` repeatable relays, `q=` the publisher's own address and label sealed,
key in `#k=`). HKDF-SHA256 with a 32-zero-byte salt and info strings
`kelp/v1/content`, `kelp/v1/swarm`, `kelp/v1/relay`, `kelp/v1/link`. **Every bundle is
encrypted**; there is no public/private distinction, so swarm is a distribution
choice, not a visibility one. A **passphrase link** is the same capability carried
in two pieces: `#p=` wraps the master secret under `PBKDF2-HMAC-SHA256` (the user's
choice over Argon2id — zero new dependencies; the count rides in the link so it can
rise later), the bundle id is the associated data, and the passphrase is stored
nowhere, so the *wrapped blob* in the row is what a restart re-mints from. LAN transport is deliberately plain HTTP — the
content is ciphertext and hash-verified, Qt 5.6 cannot do TLS 1.3 + ALPN, and the
cost (an on-path sniffer learns the token, not the plaintext) is recorded in
`kelp-design.md` §3.1. A relay serves publisher tunnels and recipient fetches on
one port, told apart by the first byte, because a link's `r=` can only name one
address. Unknown bundle, unshared bundle and wrong token all answer 401 — no
enumeration oracle. UI says **folder**, never directory. Also parked, and not to
be touched: `ipfs-fileshare-PLAN.md`.

**A received bundle is a one-shot** (2026-10-20, after a "keep received
bundles" plan was written and declined): its files are saved as ordinary files,
but **no key and no row are kept**, and its objects are free to be pruned once
nothing needs them. The vanishing is deliberate — receiving a link must not
leave a capability on this device. So "keep what you receive", opening a
received page later, and seeding a received bundle are **not** missing features;
they are the thing the app refuses to do.

23. **Scheme activation: a tapped `kelp://` link reaches Kelp** (plan written first, in
    `META-INF/scheme-plan.md`). **Done.** The desktop file now claims
    `x-scheme-handler/kelp` and runs the app through the platform launcher
    (`Exec=/usr/bin/invoker --type=silica-qt5 -- /usr/bin/harbour-kelp %u`, no `-s`: it drops
    the URL), and the spec's `%post`/`%postun` rebuild the desktop database GIO resolves the
    handler through. A new `src/kelphandoff.{h,cpp}` is the door: the first process binds
    `<data>/link.sock` (`0600`) before the UI exists; a later activation validates the URL at
    both ends (`kelp://` only, 1–4096 bytes, one line, no control characters), hands it over
    and exits; the running instance logs only *that* a link arrived, shows **Open a link**
    with it prefilled, and replaces the link on the page that is already there instead of
    stacking pages. Nothing is fetched, saved or unlocked by the activation itself, and the
    URL is never written to the log. `tst_kelphandoff` pins the validation, the wire answers
    (`ok`/`no`), one listener (a live socket is not stolen even when the caller thinks it is
    stale), `0600`, and the stale-socket rule: **51 checks**; all suites
    **1250 checks**, QML smoke **9/9 Ready**.
    On the emulator, with the i486 RPM installed: `gio mime x-scheme-handler/kelp` names the
    handler; a cold `gio open` starts the app *sandboxed* (invoker → firejail, `Seccomp 2`,
    `NoNewPrivs 1`), foreground, with the page prefilled; a link sent while Kelp is in the
    background reaches the running instance and exactly one process remains (the forwarder's
    own log line, then the instance's, ~8 ms apart); a socket left behind by a killed process
    is replaced by the next launch; two links in a row do not grow the stack
    (`pageStack.depth` stays at 2) and replace the page's link (proved with a temporary hook,
    restored and md5-checked); and the icon launch is unchanged — lipstick runs the `Exec` as
    given, so Sailjail is applied exactly once, and tapping the icon while Kelp was running
    raised the same window (the PID did not change). That was the regression this change could
    have caused.
    One honest limitation, found by the same device work: **a running, backgrounded Kelp
    cannot bring itself forward.** `requestActivate()` is ignored (Qt 5.6 has no activation
    protocol a background client may use), `invoker --single-instance` does not raise a PIE
    app, Lipstick's `WindowModel.launchProcess` answers *not in privileged group*, and a
    notification without a "default" action only dismisses on tap (Lipstick's own notification
    UI opens an app only through such an action, which would still have to raise the window
    itself). No notification was shipped on that basis. The link is waiting on the page, and
    tapping Kelp's icon raises it as usual; the cold case comes forward because a new window is
    mapped. Recorded in `scheme-plan.md` and design §2.1 rather than papered over.
