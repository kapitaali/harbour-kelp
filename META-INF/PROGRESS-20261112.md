# Progress — 2026-11-12

## run-emu-share `--relaunch` and the advertised address

### Symptom

After the machine rebooted, `src/tests/run-emu-share.sh --relaunch` advertised
the wired `10.42.0.228` instead of the phone-hotspot address; the expected
address was `172.28.172.3`, so the emitted links named a network the phone
cannot reach.

### Root cause

- The Wi-Fi radio was **off** after boot (`nmcli radio wifi` → disabled,
  `wlp3s0` had no IPv4 address). The script prefers a wireless address only when
  one exists, so it fell back to the default route — by design, with a note.
- `172.28.172.3` was not on this machine at all. The script cannot advertise it:
  the `ssh -L` forward binds the address here, and a link naming an address the
  host does not own answers nothing.

### Changes

- The host's NetworkManager profile `ei hyvää päivää`
  (UUID `fa2bd4bc-5299-4d85-a6ff-0b328b8e3a33`) is now **manual**:
  `172.28.172.3/24`, gateway `172.28.172.1`, DNS `172.28.172.1 1.1.1.1`
  (`ipv4.ignore-auto-dns yes`). The hotspot address is now stable across
  reboots, instead of the DHCP lease (which had become `.4`).
- `src/tests/run-emu-share.sh`:
  - `KELP_HOST` sets the address from the environment; `--host` still wins.
  - A wireless device with no address now prints a loud note: the Wi-Fi is off
    or not associated, the advertised address is the wired one, and a phone on
    its own hotspot cannot reach it (`nmcli radio wifi on` / `--host`).
  - The chosen address is checked against the host's own addresses. An address
    this machine does not own is refused with the list of the ones it does,
    instead of failing later as a forward that cannot bind.
  - The "no link in the log" line now says why: a release build never writes
    links, so a link has to come from the Share page (or a dev build).
- `META-INF/BUILD.md` describes the ownership rule and the warning.

Only the test helper and a doc changed; nothing here is packaged in the RPM.

### Verification

- `--relaunch` picked the Wi-Fi address and the app logged
  `KelpServer: serving on "172.28.172.3:35773"`; the forward became
  `172.28.172.3:35773 -> 10.0.2.15:35773 (guest)`.
- From the phone (`172.28.172.1`), `curl http://172.28.172.3:35773/v1/bundle/x/info`
  answered `401` in 5 ms — the forward is reachable across the hotspot. `401` is
  the expected answer for a bundle the publisher does not know.
- With the radio off the new note appears, followed by the "advertising ..."
  mismatch error; with the radio on again `172.28.172.3` is back.
- Before the pin, `--host 172.28.172.3` was refused with the local-address list
  (the address was not owned yet).
- `--fetch` was not exercised: the emulator runs the **release** build (dev
  extras off), so a restored share writes no link to the log. `--fetch` needs a
  freshly sealed share from a dev build, or a link copied from the Share page.

### Notes

- `172.28.172.3` lies inside connman's `TetheringSubnetBlock 172.28.172.0/24`
  on the phone. The phone's ARP now maps `.3` to this host's Wi-Fi MAC, but the
  tethering DHCP server could offer `.3` to a new client in principle; a
  reservation on the phone would make the pin fully safe (not done here).
- The emulator had to be started again after the reboot: the user ran
  `sudo modprobe -r kvm_intel kvm` first, then `sfdk emulator start`.
- The exact address and gateway are private LAN details; they belong in this
  gitignored note and in the host's NetworkManager profile, not in shipped
  files.
